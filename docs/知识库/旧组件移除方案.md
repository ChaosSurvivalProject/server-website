# 旧组件移除方案（生产迁移与上线验证后）

> 关联：[总体改造方案](./wiki与知识库打通改造方案.md)、[存量数据迁移方案](./存量数据迁移方案.md)。
> 本文说明：生产完成迁移、上线验证并度过观察期后，**旧 wiki（VitePress 文件站）、`kb_migrate.py`、`kb_sync.py` 及相关配置/规约如何移除，以及为什么必须移除**。

---

## 1. 移除对象与边界

| 名称 | 具体对象 | 处置 |
| --- | --- | --- |
| **旧 wiki** | VitePress 文件站：`wiki/` 整个目录（`*.md`、`.vitepress/config.mts`、`package.json`、`public/doc-image/`、`index.md` 等） | **整体删除** |
| **迁移脚本** | `backend/kb_migrate.py`（一次性迁移/校验/回滚工具） | **删除** |
| **同步脚本** | `backend/kb_sync.py`（按 MD5 增量同步的 CLI） | **删除** |

> ⚠️ **术语边界**：这里移除的是**文件形态的 VitePress 站点**，不是面向用户的知识库可视化。公开 URL `/wiki/` 与「Wiki = 知识库可视化展示」这个概念继续存在，只是改为后端 SSR 渲染。删的是旧实现，不是新展示层。

## 2. 移除前置条件（门禁，全部满足才动手）

1. [ ] 迁移脚本 `--verify` 全过：19 篇文档、187 条切片、9 张图片、3 篇 manual 文档均已就绪（见迁移方案 §6）。
2. [ ] web 已切到 SSR，`/wiki/` 与 19 个旧 URL 全部 200，`sitemap` / canonical / OG / FAQ 与迁移前一致。
3. [ ] RAG 抽样问答、FTS 抽样检索、后台增删改查与右键菜单均正常。
4. [ ] **观察期 ≥ 1–2 周**，无回退需求；数据库备份与 `kb-assets` 备份仍在有效期内。
5. [ ] 旧 wiki 目录、`kb_migrate.py`、`kb_sync.py` 已完整归档到**仓库外**的备份位置（见 §5.3）。

任一不满足 → 不进入移除流程，继续保留旧组件以便回退。

## 3. 为什么必须移除（而不是「留着备用」）

1. **幽灵数据风险（核心）**：`kb_sync.py` 固定 `WHERE source_type='wiki'`，且会扫描 wiki 目录里全部 `*.md`。迁移后新库里 19 篇文档已挂到 `kb_nodes` 树、`source_type` 仅作为废弃列保留。若有人按旧习惯再跑一次 `kb_sync.py --all`，它会**把 19 篇文档作为 `source_type='wiki'` 重新插入一遍**，产生文档树之外、后台按树找不到、但 RAG 会命中的幽灵数据。旧脚本 + 旧文件同时存在 = 随时可被触发的数据污染。
2. **消除双真相源**：留着 `wiki/` 目录会让人以为还能「改 md → 同步」，与「后台文件树是唯一维护入口」的新口径冲突；后续开发也可能按旧规约把逻辑改回去。
3. **迁移脚本不是日常工具**：`kb_migrate.py` 携带 `--apply / --rollback`，常驻会被误用为常规同步或回滚通道，且它的 `migration_v1_done` 幂等标记只在一次性场景有意义。
4. **成本与体积**：VitePress 的 `build-wiki` 阶段、`node_modules`、`.vitepress/cache|dist` 随镜像与 CI 长期占用构建时间和体积；服务器 2C2G 尤其不划算。
5. **规约一致性**：`AGENTS.md`、`docs/agents/kb.md` 里仍写着「wiki 是知识库单一数据源」，不清理会让新成员和 AI 按旧规约改代码。

## 4. 移除清单（按代码 / 配置 / 镜像 / 文档分层）

### 4.1 文件与脚本

| 对象 | 处置 |
| --- | --- |
| `wiki/`（整个目录） | `git rm -r wiki/`，含 `.vitepress/config.mts`、`package.json`、`package-lock.json`、`public/`、`index.md`、三大分区 md |
| `backend/kb_migrate.py` | `git rm` |
| `backend/kb_sync.py` | `git rm` |

### 4.2 后端代码与配置

| 位置 | 清理内容 |
| --- | --- |
| `backend/app/config.py` | 删 `wiki_dir` / `wiki_exclude` 字段及 `KB_WIKI_DIR` / `KB_WIKI_EXCLUDE` 读取 |
| `backend/.env` / `.env.example` | 删 `KB_WIKI_DIR`（含注释）；新增的 `KB_ASSET_DIR` 保留 |
| `backend/app/kb.py` | 删 wiki 来源分支：`admin_delete_document` 的 400 拒绝、`admin_reindex_document` 读 `KB.wiki_dir` 的分支、`source_type="wiki"` 写入；`KBDocumentOut.source_type` 与筛选参数从后台 API 移除（DB 列保留以兼容回退，但不再对外） |
| `backend/app/kb_ingest.py` | 模块 docstring 里「`backend/kb_sync.py` 同步 CLI」一行删掉 |
| `backend/app/database.py` | 把 `WAL` / `busy_timeout` 注释里对 `kb_sync.py` 的引用改为通用表述（**PRAGMA 本身保留**，多进程/并发写仍需要）；`KBDocument` 列注释同步 |
| `backend/crontab` | 删 `0 3 * * * … kb_sync.py --incremental` 行与 `KB_WIKI_DIR=/app/wiki`；四条任务改三条，头部注释同步（仍保留 6 段格式与「cron 不继承 env」提醒） |
| `backend/app/main.py` | 若仍有 `kb_sync` 相关启动逻辑，一并清理 |

> 保留 `source_type` / `source_path` 等 DB 列是为了**回退兼容**（旧镜像读旧列不报错），不是业务继续使用；文档里要写清这一点。

### 4.3 部署与构建

## 5. 执行顺序

### 5.1 开发 / CI 侧（准备下一个 Release）

1. 按 §4 完成代码、配置、文档清理；本地/测试环境重新构建并跑一遍冒烟（19 页 URL、后台树 CRUD、RAG 问答、cron 任务表）。
2. 用 `grep` 做残留检查（见 §6），确认无 `kb_sync` / `kb_migrate` / `KB_WIKI_DIR` / `wiki_dir` / `build-wiki` 引用。
3. Release 说明注明：「本次移除旧 wiki / kb_sync / kb_migrate，需先完成迁移方案 §7 的上线验证」。

### 5.2 服务器侧（只 pull，不 build）

```bash
cd /opt/xqly-website   # 以实际 compose 目录为准
docker compose pull
docker compose up -d --no-build
docker compose exec -T xqly-website-backend crontab -l   # 确认只剩 3 条任务
docker compose config | grep -i wiki                      # 应无 wiki 挂载/环境变量
```

- 新镜像里已没有 VitePress 静态产物、没有 `kb_sync.py` / `kb_migrate.py`；数据库不动（`source_type` 等列保留，向前兼容）。
- 切流后继续观察 1–2 周；期间若出问题，用上一个 Release tag 回退（见 §7）。

### 5.3 宿主侧清理（观察期结束后）

```bash
# 1) 归档旧 wiki 与备份到仓库外位置（保留可恢复性）
tar czf /opt/backups/xqly-wiki-legacy-$(date +%Y%m%d).tgz wiki/
# 2) 确认备份可列出内容后，再删除宿主旧目录
tar tzf /opt/backups/xqly-wiki-legacy-$(date +%Y%m%d).tgz | head
rm -rf wiki/
# 3) kb-assets 备份同理，确认无回退需求后清理旧备份
```

- **先归档、再校验、最后删除**；顺序不可颠倒。
- 归档包放在仓库外（如 `/opt/backups/`），不提交公开仓库。
- `backend/data/announcements.db.bak-*` 与 `kb-assets.bak-*` 按运维备份策略保留一段时间，不与 wiki 归档同时删除。

## 6. 残留检查与验收

开发侧执行（应**无输出**或只剩历史文档里的导航提示）：

```bash
grep -rnE 'kb_sync|kb_migrate|KB_WIKI_DIR|wiki_dir|wiki_exclude|build-wiki' \
  --include='*.py' --include='*.ts' --include='*.vue' --include='*.yml' \
  --include='*.conf' --include='Dockerfile' --include='crontab' \
  backend admin-frontend web .github docker-compose.yml 2>/dev/null
```

验收清单：

- [ ] `wiki/` 目录、`backend/kb_sync.py`、`backend/kb_migrate.py` 已从仓库与镜像中消失。
- [ ] `docker compose config` 无 wiki 挂载与 `KB_WIKI_DIR`；`KB_ASSET_DIR` 正常。
- [ ] 容器内 crontab 只剩 3 条（github_sync / staff_expire / forum_purge）。
- [ ] `/wiki/` 与 19 个页面 URL 200，图片 `/doc-image/*` 200，SSR head 与迁移前一致。
- [ ] 后台无「来源」筛选、无 wiki 只读提示，树操作与删除均可用。
- [ ] RAG 抽样问答、FTS 抽样检索正常；`index_version` 热更新仍生效。
- [ ] `web/nginx.conf` 与 `for-deploy/xqly-app.conf` 的 `/wiki/` 规则一致，1panel 配置回服务器核对过。
- [ ] 历史文档只加了「已下线」提示，归档文件未被改写。
- [ ] 旧 wiki 归档包在仓库外且校验可读；备份保留期明确。

## 7. 回退

| 场景 | 操作 |
| --- | --- |
| 新 Release 上线后发现问题（观察期内） | `IMAGE_TAG` 指回上一个 Release tag，`docker compose pull && up -d --no-build`；数据库结构向前兼容（旧列都在），旧静态产物在该镜像里 |
| 宿主 wiki 已删除但需要恢复 | 从 `/opt/backups/xqly-wiki-legacy-*.tgz` 解包回 `wiki/` |
| 数据库需要回退 | 用迁移前的 `announcements.db.bak-*` 还原，并切回旧镜像；注意这会丢失观察期内新增的知识库文档，需评估 |

> 观察期结束后不建议长期保留双栈并行：两套维护入口并存会重新引入「双真相源」，回退只作为应急手段。
