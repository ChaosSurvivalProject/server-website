# 知识库存量数据迁移方案（wiki → SQLite + 静态资源目录）

> 关联：[wiki与知识库打通改造方案](./wiki与知识库打通改造方案.md)（总体架构与术语约定）、[旧组件移除方案](./旧组件移除方案.md)（上线验证后清理旧组件）。
> 本方案覆盖**一次性迁移**：把现有 19 篇 wiki Markdown、层级配置、SEO 元数据、静态图片、以及库中已有的 manual 文档，迁入改造后的知识库（SQLite）与静态资源目录。迁移完成后 `wiki/` 目录、VitePress 构建、`kb_sync.py` 定时任务全部下线，文档管理只走知识库后台。

## 1. 迁移对象盘点（2026-11-28 实测）

| 对象 | 现状 | 数量 / 体积 |
| --- | --- | --- |
| wiki Markdown | `wiki/**/*.md`，含首页 `index.md` | **19 篇** |
| 已入库文档 | `kb_documents` 中 `source_type='wiki'`，`source_path` 为相对路径 | **19 行**，全部 `status=ready` |
| 切片与向量 | `kb_chunks.embedding`（float32 BLOB）+ `kb_chunks_fts` | **187 条切片，全部有向量** |
| 层级结构 | `wiki/.vitepress/config.mts` 的 `themeConfig.sidebar` | 3 个一级分区 + 4 个折叠子组 + 首页 |
| SEO 元数据 | frontmatter `description`（部分页面有）；`FAQ_JSON_LD` 仅进服指南页；`transformHead` 逐页 canonical/OG | 需单独抽取 |
| 静态图片 | `wiki/public/doc-image/*.png` | **9 个 PNG ≈ 3.97 MB**，md 中 **9 处引用**（8 个 `<img>` + 1 个 `![img]()`） |
| 站点图标 | `wiki/public/favicon.ico`、`logo.png` | 展示层模板用，不进知识库 |
| manual 文档 | `source_type='manual'` | **3 篇**（其中 1 篇带原件 `v1.1.3.md`，但默认上传目录里找不到该原件） |
| 索引状态 | `kb_settings`：`embed_model=BAAI/bge-m3`、`embed_dim=1024`、`index_version=17` | 迁移后只 bump 一次 |

> 关键有利条件：19 篇 md 的 MD5 与库内 `content_hash` 一一对应、187 条切片向量齐全。**只要 MD5 一致就不必重算 Embedding**，迁移主要是「补节点、补路径、补正文、搬图片」。

## 3. 迁移步骤

### 3.1 前置检查（只读，先跑 `--check`）

1. **备份数据库**：`cp backend/data/announcements.db backend/data/announcements.db.bak-YYYYMMDD`。
2. **Embedding 一致性**：确认 `kb_settings.embed_model/embed_dim` 与 `backend/.env` 的 `KB_EMBED_MODEL/KB_EMBED_DIM` 一致。
   - ⚠️ **FLPR-22「引导式全量重建」目前只是候选工单，尚未开发**。现有 `kb_sync.py --all --force` 不能用于换模型/维度：`--force` 只解除一致性拒绝，**不会重嵌 MD5 未变的文件**（换模型但 wiki 未改时 `created/updated=0`，不写回 `embed_model`/`embed_dim`、不 bump `index_version`），且固定 `WHERE source_type='wiki'` 漏掉 manual 文档——结果向量仍是旧维度。
   - 因此：若一致，直接迁移（复用向量）；若不一致，**把「全量重嵌」作为本迁移脚本的内置能力**：忽略 MD5 判重、覆盖 wiki + manual 全部文档、写回 `kb_settings.embed_model/embed_dim`、bump `index_version`、并保证 `vector_available` 恢复（当前 `startup_check` 一旦置 False 无运行时恢复路径）。改 `backend/.env` 的配置需先重启后端加载新配置，索引热更新在迁移完成后自动生效、无需再次重启。
3. **MD5 对账**：逐文件算 MD5 与 `content_hash` 比对，输出三类清单：
   - 一致（预期 19 篇）→ 复用向量；
   - 不一致（wiki 改过但 cron 未跑）→ 标记需重算 Embedding；
   - 库内有但文件不存在 → 按 `--prune` 语义处理。
4. **资源对账**：列出 9 个 PNG 的 md5 / 大小 / 引用页面，确认目标目录无同名冲突。
5. **停同步**：迁移期间暂停 `kb_sync` cron（`CRON_ENABLED=0` 或临时注释），避免并发写库。

脚本形态：`backend/kb_migrate.py --check / --apply / --verify / --rollback`，沿用 `kb_sync.py` 的 WAL + `busy_timeout=8000` 连接方式； SQLite 允许服务端在线读，迁移进程单跑。

### 3.3 文档正文迁移与切片复用

对每篇 wiki 文档：

1. 读取源文件，**去掉 frontmatter** 后作为 `content_md` 落库；保留 `:::` 容器、`<img>` 标签、Heading，交给 SSR 渲染器处理。
2. 从 frontmatter 抽 `description` 写入节点 `description`；无 frontmatter 时用标题 + 站点描述兜底。
3. MD5 与 `content_hash` 一致：
   - **复用**现有 `kb_documents` 行与 187 条 `kb_chunks`（含向量、FTS 行不动）；
   - 只补 `node_id`、`content_md`、`slug`、`published=1`。
4. MD5 不一致：走与 `kb.py::_ingest_document` 相同的重建流程（删旧切片/FTS → 重新切片 → Embedding → 落库），保证检索与展示同版本。
5. 首页 `index.md` 挂 `slug=''` 的文档节点，URL `/wiki/`；`slug` 唯一约束允许恰好一个空值。

对 3 篇 manual 文档：

- 统一挂到新建的「未分类」目录（`folder`，`published=0`）；
- `slug` 用 `manual/<id>-<标题slug>` 生成并做唯一性校验，避免与 19 篇冲突；
- `published=0`（草稿）——这与现状一致：manual 文档只在后台可见，从未在可视化层公开；
- 切片/向量原样保留，不重算。

### 3.4 静态资源迁移

1. 新增配置 `KB_ASSET_DIR`（默认 `/app/data/kb-assets`），`docker-compose.yml` 挂持久化卷；`web/nginx.conf` 与 `for-deploy/xqly-app.conf` 同时加 `location /doc-image/ { alias /app/data/kb-assets/doc-image/; }`（两份配置必须同步）。
2. `cp -a wiki/public/doc-image/. → $KB_ASSET_DIR/doc-image/`。
3. 逐文件 `md5sum` 比对，生成 `backend/data/migration-manifest.json`（文件名 / 大小 / md5 / 引用页面），作为验收与回滚依据。
4. **正文里的 `/doc-image/xxx.png` 一个字都不改**——URL 保持不变是这次迁移能低成本完成的关键。
5. `favicon.ico` / `logo.png` 归 web 静态目录，由展示层模板引用，不进知识库数据目录。
6. 9 个 PNG 全部被 md 引用（8 个 `<img>`、1 个 `![img]()`），无孤儿文件。

### 3.5 收尾

- 全量迁移成功后**自增一次 `index_version`**：服务端下次对话自动重建内存索引，无需重启（不能退化成「重启生效」）。
- 写 `kb_settings.migration_v1_done=1`，脚本可重复执行且自动跳过已完成项（幂等）。
- 迁移完成后保留 `wiki/` 源目录和 VitePress 产物直到 P2 流量切换验收通过，再按总体方案 P3 清理。

## 4. 迁移脚本设计

`backend/kb_migrate.py`（一次性工具，迁移验证通过后删除）：

| 参数 | 行为 |
| --- | --- |
| `--check` | 只读：MD5 对账、资源对账、输出将创建的节点/文档/资源清单 |
| `--apply` | 执行：种子树 → 补文档字段 → 搬资源 → 必要时重建切片 → bump `index_version` |
| `--verify` | 校验：19 个 URL、187 条切片、9 个资源 md5、FAQ/description、RAG 抽样问答 |
| `--rollback` | 从 `.bak-YYYYMMDD` 恢复数据库；资源目录保留（覆盖不影响） |

实现约束：

- 与 `kb_sync.py` 同款 `PRAGMA journal_mode=WAL` + `busy_timeout=8000`，单进程执行；
- 全程**只读** `wiki/` 源文件，不写 git 工作树；
- 每张表写入放在同一事务，失败整体回滚；`migration_v1_done` 作为幂等标记；
- 不调用 `kb_sync.py`（避免 `--prune` 误删），需要重建时直接复用 `kb_ingest`。

## 5. 风险与注意

| 风险 | 缓解 |
| --- | --- |
| 文件与库内 MD5 不一致（wiki 改过但 cron 未跑） | `--check` 阶段列出清单，仅对不一致项重算 Embedding；预计 1–3s/篇，可接受 |
| 3 篇 manual 文档 slug 与正式页面冲突 | 统一加 `manual/` 前缀 + id，唯一索引兜底 |
| 原件文件缺失（已发现 `v1.1.3.md` 的默认路径下无文件） | 校验并标记，属性面板显示「原件缺失」，不阻断迁移 |
| 静态资源目录同名覆盖 | `--check` 先比对 md5；一致跳过，不一致保留两份并告警 |
| 迁移并发写库 | 暂停 cron；WAL + busy_timeout；单进程 |
| 迁移后 RAG 检索异常 | 抽样问答 + FTS 关键词检索对比；`index_version` 只 bump 一次 |
| 误把迁移脚本当长期同步用 | 脚本命名 `kb_migrate` 且迁移后删除；规约里明确「无文件同步」 |

## 7. 生产环境（Docker 镜像更新）迁移流程

生产只做 `docker compose pull && docker compose up -d --no-build`，**绝不在服务器 build**（2C2G 跑 Vite 会 OOM）。因此迁移必须设计成「**后端先行、web 后切**」：先拉带迁移脚本的新后端镜像，用一次性容器跑迁移；确认无误后再切 web 镜像，让 `/wiki/` 从静态产物切到 SSR。这样切换瞬间数据库已是新结构，不会出现 404 空窗。

### 7.1 发布前准备（开发 / CI 侧）

1. `kb_migrate.py`、SSR 路由、新 nginx 规则都进代码库，随 Release 由 `.github/workflows/release-images.yml` 构建进 `-backend` / `-web` 两个镜像。
2. Release 说明写明：本次上线需按本文 §7 执行迁移，**不能只 pull 就完事**。
3. 镜像按 Release tag 固定（`IMAGE_TAG`），不要用裸 `latest`，否则回退时找不到旧版。
4. `docker-compose.yml` 预置好新卷与环境变量（见 §7.2），但 web 镜像可保持旧版——compose 改动与新镜像解耦。

### 7.2 服务器侧一次性改动（不换镜像先做）

在 compose 文件所在目录（生产通常为 `/opt/xqly-website`，以实际 `docker compose config` 输出为准）：

1. 给 backend 服务加持久化卷与环境变量：

   ```yaml
   environment:
     - KB_ASSET_DIR=/app/data/kb-assets
     - CRON_ENABLED=0          # 迁移窗口内暂停镜像内 cron
   volumes:
     - ./backend/data/kb-assets:/app/data/kb-assets
   ```

   `./wiki:/app/wiki:ro` 在迁移期**保留**（脚本从这里读 19 篇 md 和 9 张图），清理放到观察期后。

2. 用**旧镜像**重建一次让配置生效：`docker compose up -d --no-build`。
3. 备份（宿主侧，卷路径以 `docker compose config` 为准）：

   ```bash
   cp backend/data/announcements.db backend/data/announcements.db.bak-$(date +%Y%m%d)
   tar czf backend/data/kb-assets.bak-$(date +%Y%m%d).tgz backend/data/kb-assets 2>/dev/null || true
   ```

### 7.3 执行迁移（后端先行）

```bash
# 1) 只拉新后端镜像（web 仍是旧版，/wiki/ 继续走静态产物，用户无感）
docker compose pull xqly-website-backend

# 2) 用一次性容器跑迁移，线上老后端继续服务
#    容器继承 compose 的卷与 env（含 KB_ASSET_DIR / ANNOUNCEMENT_DB），
#    与老后端同库并发写靠 WAL + busy_timeout，符合既有设计
docker compose run --rm xqly-website-backend python backend/kb_migrate.py --check
docker compose run --rm xqly-website-backend python backend/kb_migrate.py --apply
docker compose run --rm xqly-website-backend python backend/kb_migrate.py --verify

# 3) 验收通过后，把线上后端切到新镜像
docker compose up -d --no-build xqly-website-backend

# 4) 切 web：/wiki/ 由静态产物改走后端 SSR（此刻 DB 已就绪，无 404 空窗）
docker compose pull xqly-website-web
docker compose up -d --no-build xqly-website-web

# 5) 恢复 cron：新镜像 crontab 已移除 kb_sync，其余任务照常
#    把 .env 的 CRON_ENABLED 改回 1 后：
docker compose up -d --no-build
```

要点：

- 步骤 2 用 `docker compose run --rm` 而不是 `exec`：老容器里没有迁移脚本，`run` 会用刚 pull 的新镜像起一次性容器，跑完即删，不替换线上后端。
- 步骤 3 之后 `startup_check` 看到的是迁移已写回的 `embed_model/embed_dim`，`vector_available` 保持可用；若顺序颠倒（先切后端再迁移），维度不一致会先把向量检索关掉，得等迁移后恢复。
- `index_version` 在 `--apply` 末尾 bump，服务端下一轮对话自动重建内存索引，**索引数据变更全程不重启**（步骤 2 为加载新 `.env` 的那次重建属配置变更，规约允许）。

### 7.4 回退路径

| 场景 | 操作 |
| --- | --- |
| `--check` 就发现问题 | 不执行 `--apply`；compose 恢复原状，继续用旧镜像 |
| `--apply` 中途失败 | 容器内 `python backend/kb_migrate.py --rollback`，或宿主侧 `cp announcements.db.bak-* announcements.db`；`kb-assets` 是新增目录，覆盖不影响 |
| web 切流后页面异常 | 把 `IMAGE_TAG` 指回上一个 Release tag，`docker compose pull xqly-website-web && up -d --no-build`；数据库保持新结构（向前兼容） |
| 整体回退 | 旧 backend + 旧 web 镜像 tag + 备份 DB；`./wiki:/app/wiki:ro` 挂载与旧 web 镜像里的静态产物都还在 |

### 7.5 生产特有注意事项

- **1panel 配置**：`/wiki/` 路由在 web 容器 nginx 内；若 `for-deploy/xqly-app.conf` 的手工 location 里也有 `/wiki/`，必须同步改。改完**回服务器核对** conf，防止 1panel 重新生成把 `try_files` 兜底与 `include proxy/*.conf` 冲掉（AGENTS.md 部署红线）。
- **两份 nginx 配置**：`web/nginx.conf` 与 `for-deploy/xqly-app.conf` 的任何 `/wiki/` 改动都要同步，SSE 四件套不要动。
- **cron 不继承容器 env**：`CRON_ENABLED` 在 compose 的 `environment` 里，改完必须重建容器才生效；只改 `docker-compose.yml` 不 `up -d` 等于没改。
- **`.env` 含 API Key**：只在宿主侧改并挂只读卷，禁止进镜像或提交仓库。
- **观察期后再清源**：确认无回退需求后，才从 compose 移除 `./wiki:/app/wiki:ro` 挂载、删除宿主 wiki 目录与旧 VitePress 产物，并把 `kb_sync.py` / 旧 cron 行从镜像中彻底移除（下一次 Release）。
