## 2. 检索方案选型

### 2.1 候选实现与本机实测

本机实测（Python 3.13 / Windows，纯 stdlib `array` + `operator.mul` + `heapq`）：

| 实现 | 200×1024 | 500×1536 |
|---|---|---|
| 切片 + `zip` 生成式 | 8.5 ms | 31.8 ms |
| 切片 + `sum(map(mul))` | 5.4 ms | 20.2 ms |
| **预切行 + `sum(map(mul))`** | **5.2 ms** | **20.0 ms** |
| 预切行 + `heapq.nlargest` | 5.2 ms | 20.2 ms |

矩阵常驻内存（float32，实测）：

| 规模 | 内存 |
|---|---|
| 200 × 1024 | 0.78 MB |
| 500 × 1536 | 2.93 MB |
| 2000 × 1536（硬上限） | 11.7 MB |

### 2.2 结论与理由

- **不用 numpy**：最坏情况 20 ms/query，而总延迟由远端 LLM 决定（1–3 s），20 ms 是噪声。numpy 的导入开销（十几 MB 量级）已经大于整个向量矩阵。
- **不用 sqlite-vec**：它解决的问题是"10⁵ 级以上向量时不要把矩阵搬进 Python 堆"。本项目几百条向量、3 MB 以内，引它反而**增加**常驻（扩展二进制 + 虚拟表页缓存），方向是反的。
  - 关于"sqlite-vec 能否解决生产内存小的问题"——**不能，方向是反的**。真正的内存大头是运行时基线，不是向量。
- **FTS5 用 trigram**：默认 `unicode61` 不切分中文，中文检索会完全失效。

### 2.3 内存预算与硬保险

```
Python 运行时 + FastAPI/uvicorn   ≈ 80–120 MB   ← 先量这个，它决定一切
httpx                              ≈ 2–4 MB
向量矩阵（上限 2000 × 1536）        ≤ 12 MB
----------------------------------------------
合计                               ≈ 95–136 MB   128 MB 非常紧
```

**上线前必做**（不是可选项）：

```bash
# 服务跑起来后量基线（无请求状态）
ps -o rss= -p "$(pgrep -f 'app.main:app')" | awk '{print $1/1024 " MB"}'      # Linux
# 或 cgroup 口径
cat /sys/fs/cgroup/memory.current
```

- 基线 > 90 MB → **把限制提到 256 MB**，不要靠砍向量省内存（省不出那 3 MB）。
- 若确实不能提额，降级路径按序：`KB_MAX_CHUNKS=500` → 关闭向量检索只留 FTS5（`KB_VECTOR_ENABLED=0`）。
- **`KB_MAX_CHUNKS` 默认 2000**：超出时只加载最新的 N 条并打 WARNING，绝不无界增长。

## 3. 前端流式渲染选型

### 3.1 为什么不用 Streamdown

Streamdown 是 **React 专用**（`react-markdown` 的 drop-in 替代），且**必须配置 Tailwind 扫描它的 dist**（官方文档把这列为最易漏的一步）。本项目主站是 Vue 3 + 纯 CSS，没有 Tailwind，用不了。

而项目已经装好了 `marked@18` + `dompurify@3` + `highlight.js@11`，并在 `frontend/src/utils/markdown.js` 暴露了统一入口，`AGENTS.md` 契约规约第 7 条要求 Markdown 渲染必须走这个入口。**所以零新依赖复用这套管线。**

关键在于：Streamdown 的价值**不在渲染能力，在渲染调度**。逐项对齐后真正缺的只有两件事：

| Streamdown 的能力 | 本项目对应物 | 结论 |
| --- | --- | --- |
| react-markdown 等价解析 | `marked`（已配 gfm + breaks） | 等价，直接用 |
| Shiki 高亮 + 代码块工具条（语言标签 / 复制） | `hljs` + `marked` 自定义 renderer | **已有**，现有入口的输出就带 header + 复制按钮 |
| `parseIncompleteMarkdown`（补未闭合语法） | 无 | 需补，依据见 §3.2 |
| 块级 memo 渲染（只重渲染最后一块） | 无（现在是整容器 `v-html` 全量替换） | 需补，依据见 §3.3 |
| 逐块淡入 + 打字光标 | 无 | 依赖上一条；块级渲染落地后是纯 CSS，约 20 行 |

### 3.2 实测：流式中间态会不会「跳」

用项目现有配置（`marked.setOptions({gfm:true, breaks:true})` + 同款 code renderer）对 851 字客服回答做逐 token 前缀快照：

| 流式中间态 | `marked.parse` 的实际输出 | 观感 |
| --- | --- | --- |
| 未闭合围栏 ` ```bash ` | **已直接渲染为代码块**（marked 对围栏容错） | 不跳，无需处理 |
| 表格分隔行还没到 | 整行退化为段落文本 | 分隔行到达时**整块跳变**，最明显 |
| 未闭合加粗（`端口 **25565`） | 显示裸 `**25565` | 闭合瞬间跳 |
| 未闭合链接（`[指南](https://xqly.exa`） | 渲染出 `[新手指南](<a href="https://xqly.exa">…</a>` | 最脏，且跳 |
| 未闭合行内代码（`` 使用 `/spawn ``） | 显示裸反引号 | 闭合瞬间跳 |
| 列表写到一半 | 最后一项显示半截文本 | 不跳 |

这正是 Streamdown 要补 `parseIncompleteMarkdown` 的全部理由。P0 只需处理**最后一个块**（历史块不会变），补 `**` / `` ` `` / `](` / 围栏四种，约 15 行。

### 3.3 实测：成本瓶颈不在 CPU，在 DOM 重建次数

851 字回答 / 213 个 token（每 token 4 字符）：

| 方案 | 总 CPU | 单帧最慢 | 每帧 DOM 操作 |
| --- | --- | --- | --- |
| 每收到一个 token 就全量 parse | 26.7 ms | 1.07 ms（GC 抖动） | **整容器 innerHTML 赋值 213 次** |
| 80 ms 节流 + 全量 parse | 10.3 ms | 0.53 ms | 整容器 innerHTML 赋值 54 次 |
| **块级 keyed 渲染** | 11.0 ms | 0.72 ms | **只改变化的块**（27 块，单帧最多变更 3 块） |

三个可用结论：

1. **CPU 根本不是问题**——连「每 token 全量重渲染」这种最笨的写法，整篇回答也只要 26.7 ms。对照：不调 hljs 的 marked 是 14.1 ms，说明 hljs 的增量只有十几毫秒。节流该做，但理由是「少写 DOM」而不是「省 CPU」。
2. **真正的差别是 DOM 重建次数**：全量 `v-html` 每帧销毁重建全部 27 个块（54 帧 ≈ 1458 次块级重建），块级 keyed 渲染只 patch 变化的那 1–3 块。前者导致：逐块淡入动画每帧重放（**整段文字持续闪烁**）、流式中选区被清掉、`<details>` 折叠状态与图片重新加载。**只要想要「逐块淡入 + 打字光标」这个观感，块级渲染就是前提，不是优化项。**
3. **未标注语言的围栏不要调 `hljs.highlightAuto`**：实测 1.449 ms/次，是指定语言 `hljs.highlight`（0.064 ms）的 **22.5 倍**，且对半截代码做语言嗅探会给出随机配色，是负效果。

> 测量方法备注：首轮曾跑出"单帧 105 ms"，复核后确认是模块冷启动/JIT 预热，预热后重测最慢 1.07 ms 且归因于 GC。**这类数字不预热就是假的**，后续任何前端性能对比都应先预热再测。

### 3.4 块级切分的保真度（已实测，可放心用）

`marked.lexer(text)` 切块 → `marked.parser([token])` 逐块出 HTML → 拼接：

- 与整篇 `marked.parse(text)` 输出**逐字符一致**（含标题/段落/列表/代码/表格/引用/分隔线）。
- 10 个上下文依赖的边界情形**逐块渲染结果全部与整篇一致**：引用式链接与图片（定义在其他块）、脚注、紧凑 vs 松散列表、任务列表、嵌套引用内代码块、表格后紧跟列表、HTML 块、中文段落硬换行。
- 需过滤 `type === 'space'` 的空块，否则会产出空 DOM 节点。
- 代价：每帧多一次 `lexer` 全文扫描，实测总 CPU 与「80 ms 节流 + 全量 parse」基本持平（11.0 ms vs 10.3 ms）。

## 4. 其他技术取舍

| 决策 | 备选 | 理由 |
|---|---|---|
| 自写 `.env` 解析（约 20 行 stdlib） | `python-dotenv` | 省一个依赖；且能保证**已存在的进程环境变量优先**，让 systemd `Environment=` 覆盖 `.env` |
| 自写切片器（约 70 行） | `langchain-text-splitters` | 中文场景只需要递归分隔符切分；自写可控，且能顺手做标题路径前缀与代码块保护——这两件对检索质量影响最大，用现成包反而要绕 |
| 不引 LangChain / LangGraph / Agent / Tool | — | 唯一的"工具需求"是查服务器在线状态，一个关键词 `if` + 字符串拼接就够，引工具调用循环是纯负债 |
| 不引 Redis / 会话表 / 历史落库 | Redis、SQLite 会话表 | 多轮由**客户端**携带 `history` 数组，服务端无状态；省掉会话生命周期、清理、并发一致性一整类问题 |
| 不做本地 Embedding（bge-m3 等） | 本地部署 | 往 128 MB 的机器塞 torch 不可行；用厂商 API，仅支持 OpenAI 协议 |
| 不用 `mcstatus`（P0） | `mcstatus` 的 `AsyncJavaServer` | 现有 `probe_tcp` 已能答"在线/离线"，P0 够用；真实人数/版本留 P1 |
| Embedding 串行请求，不用并发/Semaphore | `asyncio.gather` + 信号量 | 摄入只发生在脚本执行与后台手工粘贴，频率极低（500 块约 16 次请求、数秒完成）。少一个并发原语 = 少一类 bug |
| FTS5 用**独立表 + 显式 `rowid`**，不用 external content 与触发器 | external content + 触发器同步 | 只需在写入/删除时手动同步两行 SQL，规避 FTS5 `'delete'` 命令一族坑位 |
| 限流状态放进程内 | Redis / 共享存储 | P0 单 worker 部署；多 worker 时需换共享存储，已记入 `TODO.md` |
| 与 LLM 交互全部走 OpenAI 协议 | 各家 SDK | 一套代码覆盖 OpenAI / DeepSeek / 通义 / 硅基流动；厂商私有开关用 `KB_CHAT_EXTRA_BODY` 原样 merge 进请求体，不为单个厂商改代码 |
| 错误分两类处理 | 统一走包络 | 流开始**前**的错误能走标准 HTTP（400/429/503 + 项目包络）；流开始**后** header 已发出，只能发 `{"error":...}` + `[DONE]`。不区分会导致"先 200 再报错"这种前端无法处理的形态 |
| `kb_sync.py` 走独立进程 CLI | `BackgroundTasks` 后台任务 | 服务用 `StaticPool` 长期持有唯一连接，`BackgroundTasks` 与请求共用一个事件循环会互相阻塞；且 P0 定的就是"线上只读、脚本维护" |
| 后台禁止删除 `source_type='wiki'` 文档 | 允许删除 | 保持 wiki 为单一数据源；否则下次 `kb_sync --all` 会把它又建回来，产生"删不掉"的错觉 |

## 5. 风险与已知取舍

| 风险 | 影响 | 处置 |
|---|---|---|
| 服务端基线内存可能已超 128 MB | 服务被 OOM kill | **上线前先量基线**（§2.3）；必要时提额到 256 MB。不要靠砍向量省内存 |
| 上游 API 抖动/超时 | 用户看到报错 | 已定：流中错误发 `{"error":...}` + `[DONE]`；前端保留已收内容 |
| 上游涨价或欠费 | 客服整体不可用 | `KB_ENABLED=0` 一键关闭，前端不渲染悬浮球 |
| 限流状态在进程内 | 多 worker 时限流不准 | P0 单 worker 部署；已记入 `TODO.md` |
| `KB_MIN_SCORE` 阈值难调 | 要么拒不答、要么胡答 | 先用 0.35 起，上线后从日志统计未命中率再调；**宁可不答也不要胡答** |
| 流式渲染时 Markdown 语法未闭合 | 中间态出现裸 `**`、未闭合链接渲染成脏文本、表格在分隔行到达前退化为段落 | 已实测（§3.2）；块级 keyed 渲染 + 末块补全，跳变只可能发生在最后一块，历史块永不回写 |
| 后台手动入库是同步阻塞请求 | 极端情况请求超时 | 单次粘贴只产生几条切片，1–3 s；admin HTTP 超时 10 s，余量充足 |
| `servers` 持久化改变了原有"重启即重置"行为 | 需人工核对线上地址 | 属修 bug；已写明在 README 变更说明，首次启动自动用原硬编码值做种子，行为等价 |
| `kb_settings.embed_dim` 与 `KB_EMBED_DIM` 不一致 | 脏检索引擎静默返回垃圾结果 | 启动时比对，不一致直接关闭向量检索并打 ERROR，后台统计页显式标记 |
