## 0. 文档说明

### 0.1 现状盘点（动手前必读，避免把已有能力重做一遍）

| 能力 | 现状（已读代码确认） | 本次要做的净新增 |
| --- | --- | --- |
| 作者删帖 | **入口已存在**：`MyPosts.vue` 行内「删除」→ `DELETE /api/forum/articles/{id}`（`backend/app/forum.py:1266`）→ 软删 `status=3` + `remove_by='author'` | 语义改为**进回收站**（`status=4`）；新增**回收站独立页面**、**恢复**、**彻底删除**、**30 天超期自动清理** |
| 删帖后的找回 | 无任何恢复入口：`status=3` 只作为"已下架"展示；作者只能靠**编辑重提**（重走审核）找回 | 回收站页面 + 恢复（不重审，回删除前状态） |
| 作者删评论 | **完全没有**：主站 `CommentSection.vue` 注释仍写"第一阶段无删除入口（§8-D16）"，`frontend/src/api/api.js` 无 `deleteComment`，后端**无** `DELETE /comments/{id}` | 主站删除入口 + 后端新接口（物理删除，不留痕） |

| 管理员删帖 | 有：`DELETE /api/forum/admin/articles/{id}` → **物理删除** + 级联清理（`_cascade_delete_article`） | 保持不动；后台列表**新增回收站筛选档**与"恢复"扩展 |
| 回收站概念 | **零存在**：主站、后台、`forum.py` 全仓 `grep "回收站\|recycle\|trash"` 无命中 | 全新概念 |

> 因此 Floyd 说的"目前帖子和评论不支持删除"**对评论完全成立**；对帖子是"有一个只隐藏、不能恢复、且已下架行连按钮都没有的删除"——本 PRD 把它补成真正的删除/恢复闭环。

### 0.2 一句话目标与范围

**一句话目标**：作者能真正删掉自己的帖子和评论——帖子进回收站、30 天内可一键恢复、超期自动清除；评论删了就没了，不留占位、不留痕迹。

**范围内**：

| # | 内容 |
| --- | --- |
| 1 | 帖子：作者删除 → 回收站（新增 `status=4`）→ 30 天内恢复 → 超期自动物理清除 |
| 2 | 帖子：回收站内可**彻底删除**（立即物理删除，不可恢复） |
| 3 | 评论：作者删除自己的评论/回复 → **物理删除**（顶层连带其下全部回复），`comment_count` 同步 |
| 4 | 前端：**回收站独立页面 `/forum/recycle`**（入口按钮「查看已删除文章」）、我的文章页删除口径修正、详情页作者删除入口、评论区删除入口、状态文案表同步 |
| 5 | 后台：文章列表「回收站」筛选 + 恢复；评论抽屉保持现状 |
| 6 | 基础设施：`forum_articles` 补 3 列 + 存量迁移；`backend/forum_purge.py` CLI（crontab 每日 + 启动兜底） |

**明确不做**（顺延，勿顺手做）：

| 不做的事 | 理由 / 归属 |
| --- | --- |
| 评论**编辑** | 原"评论作者自删与编辑"条目只取"自删"这一半；编辑的权限与留痕边界另议（第二阶段） |
| 楼主 / 版主删除**他人**评论 | 第一阶段无版主概念，删他人内容一律走管理员后台 |
| 删除审计日志（谁在何时删了什么） | 与"评论删除无需留痕"直接冲突；帖子侧留痕靠回收站本身 |
| 删除 / 恢复的站内信通知 | 站内信本身是第二阶段 |
| 回收站的**批量**操作（批量恢复 / 批量清空，或一键清空回收站） | 逐条操作够用；批量与本阶段的治理诉求无关 |
| 回收站正文预览 | 要看就先恢复（§6-D4） |
| 删除时的图片文件清理（封面图 / 正文内嵌图） | 「图床冗余文件清理」是第三阶段明确顺延项 |
| 评论删除后显示"该评论已删除"占位 | 与"无需留痕"冲突 |
| 后台回收站页 / 回收站统计看板 | 治理用不上，后台只要能在文章列表里筛出来并恢复 |

### 0.3 术语

| 术语 | 含义 |
| --- | --- |
| 回收站 | 帖子被作者删除后的**保留态**（`status=4`）：对全站不可见，但数据完好，30 天内作者可恢复 |
| 恢复 | 回收站帖子回到**删除前的状态**（不是重走审核，内容零改动） |
| 彻底删除 / 硬删 | 物理 `DELETE` 行 + 级联清理关联表，**不可恢复**（作者可在回收站主动做，管理员后台一直能做） |
| 超期清理 | `deleted_at` 距今 > 30 天的回收站帖子由 CLI 物理清除 |
| 不留痕（评论） | 物理删除行：无占位、无 `status=2` 残留、无审计表、无日志表 |
| `daysLeft` | 后端算好的剩余可恢复天数（前端只显示，不自己算） |

## 1. 帖子删除与回收站

### 1.1 状态机（在 §4.3 第一阶段状态机上的新增与收窄）

```
新增（作者侧）
  0 待审核 ──(作者删除)──▶ 4 回收站   [status_before_delete=0, deleted_at=T]
  1 已发布 ──(作者删除)──▶ 4 回收站   [status_before_delete=1, deleted_at=T,
                                       publish_time_before_delete=原 publish_time, 标签 use_count -1]
  2 已驳回 ──(作者删除)──▶ 4 回收站   [status_before_delete=2, deleted_at=T]
  4 回收站 ──(作者恢复, ≤30 天)──▶ status_before_delete
                                     [回到 1 时：标签 use_count +1、publish_time 回填原值]
  4 回收站 ──(作者「删除」/ 管理员硬删 / 超期清理)──▶ 物理删除（级联，不可恢复）

收窄（管理员侧，语义不变）
  1 已发布 ──(管理员下架)──▶ 3 已下架  [remove_by='admin']     ← status=3 从此只有这一个来源
  3 已下架(admin) ──(作者删除)──▶ 400「该帖已被管理员下架，请联系管理员处理」
  3 已下架(admin) ──(作者编辑)──▶ 400（第一阶段 §8-D9 既有规则，不改）

不变（既有规则，逐字保留）
  任意状态 ──(作者编辑保存)──▶ 0 待审核（resubmit_count +1，互动数据全保留）
```

> **`_set_article_status()` 仍是 status 的唯一转移点**（第一阶段 §8-D8）：`1 → 4` 属于"离开已发布"，标签 `use_count` -1、`publish_time` 清空；`4 → 1` 属于"进入已发布"，`use_count` +1。恢复路径需要**回填 `publish_time`**，实现方式二选一（推荐前者，不破坏单点结构）：
> 1. 给 `_set_article_status()` 加可选参数 `publish_time_override: Optional[str] = None`，进入 `status=1` 时若传入则用它替代 `_now_iso()`；
> 2. 恢复流程里先 `_set_article_status(1)` 再手工把 `publish_time` 覆盖回原值（同事务，但多一处"绕过单点写 publish_time"，不推荐）。

### 1.2 数据模型变更（`forum_articles` 补 3 列 + 迁移）

| 新列 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `deleted_at` | 字符串(30) | `''` | 进回收站的北京时间 ISO；`''` = 不在回收站。**30 天判定唯一权威** |
| `status_before_delete` | 整数 | `0` | 恢复目标状态（只可能是 0 / 1 / 2） |
| `publish_time_before_delete` | 字符串(30) | `''` | 删除前的 `publish_time`，恢复时回填（§0.4-D 防刷榜）。删前非已发布则为 `''` |

- `status` 枚举扩展为 **0 待审核 / 1 已发布 / 2 已驳回 / 3 已下架（仅管理员）/ 4 回收站**；后端 `ARTICLE_STATUS_TEXT` 增 `4: "回收站"`（**后端是唯一权威**，前端 5 处文案表同步，见 §3.5）。
- 迁移函数 `migrate_forum_article_recycle_columns()`（仿 `migrate_user_mute_column` 的写法：`PRAGMA table_info` 判断列是否已存在 → 幂等 `ALTER TABLE ADD COLUMN`），在 `init_db()` 末尾与其它 `migrate_*` 并列调用；**新库由 `create_all` 直接建全，迁移跳过**。
- 存量回填（同一次迁移内，幂等：只影响 `status=3 AND remove_by='author'` 的行）：
  ```sql
  UPDATE forum_articles
     SET status = 4,
         status_before_delete = 1,
         deleted_at = update_time,
         publish_time_before_delete = ''      -- 存量无法还原原发布时间，恢复时兜底为当前时间
   WHERE status = 3 AND remove_by = 'author';
  ```
  > 该语句会让"30 天窗口"从**原有 `update_time`** 起算——即历史上早就自删掉的帖子可能在首次清理时被直接物理删除。实施前先数一遍行数（`SELECT count(*)`），若确有需要保留的历史帖，先人工决定是否把 `deleted_at` 改写为迁移时刻。
- 评论表 `forum_comments` **不加列、不改结构**（"不留痕"= 直接删行，见 §2）。

### 1.3 删除 / 恢复 / 彻底删除 / 超期清理

| 动作 | 触发 | 规则 |
| --- | --- | --- |
| 删除（进回收站） | 作者在详情页 / 我的文章页点「删除」 | 校验：本人（否则 404）、状态 ∈ {0,1,2}（`3 & admin` → 400，已在 4 → 400「该帖已在回收站」）；写 `status_before_delete` / `deleted_at` / `publish_time_before_delete`；`_set_article_status(4)`；`remove_by='author'`；`update_time` 刷新 |
| 恢复 | 作者在回收站点「恢复」；管理员在后台点「恢复」 | 校验：`status=4`；`now - deleted_at ≤ 30 天`（超期 **410 Gone**，`detail="已超过 30 天保留期，无法恢复"`）；恢复目标 = `status_before_delete`（回到 1 时标签 +1、`publish_time` 回填 `publish_time_before_delete or 当前时间`）；清空 `deleted_at` / `status_before_delete` / `publish_time_before_delete`；`remove_by=''` |
| 彻底删除 | 作者在回收站页面点行内**「删除」**；管理员后台点「删除」 | 立即物理删除 + 级联（复用 `_cascade_delete_article`：评论、评论点赞、帖子点赞、收藏、标签关联；若删前是已发布且尚未扣减则标签 -1——`status=4` 已在回收站，扣减不会重复） |
| 超期清理 | `backend/forum_purge.py`（crontab 每日 05:00 + `main.py` 启动兜底一次，均 `--dry-run` 可预览） | 物理删除 `status=4 AND deleted_at < now-30d` 的全部帖子（逐条走同一 `purge_due()`，与用户路径共用语义）；输出清理条数到日志 |

**为什么清理不能只靠 crontab**：与员工名片同款理由——判定权威是 `deleted_at`，恢复接口自己校验、列表自己过滤，**漏挂 crontab 只是"数据多留几天"，不会让用户恢复出超期内容**。

### 1.4 可见性与互动封锁

- `_can_view_article()` 增一条：`status == 4 → False`（对**所有人**，含作者与管理员）。于是公开接口在回收站帖上一律 404：`GET /articles/{id}`、`GET /articles/{id}/comments`、`POST /articles/{id}/like|favorite|comments`、`GET /articles/{id}/author-posts`；`POST /articles/{id}/view` 本来就只认 `status=1`（现有实现已是 `WHERE status=1`），自然 404。
- 回收站列表由 `/api/forum/my/articles?status=4` 提供（**自己取数据，不经过详情接口**），列表项额外下发 `deletedAt` / `daysLeft` / `statusBeforeDelete`。
- **不做回收站正文预览**：要看完整内容先恢复（恢复是零风险操作）。后台管理员可用 `GET /api/forum/admin/articles/{id}` 看全量（该接口不依赖 `_can_view_article`，不受影响）。
- 回收站帖不出现在：首页 / 板块列表（只查 `status=1`）、推荐聚合、`GET /forum/stats`、作者卡"其他帖子"、用户论坛数据（发帖数 = 已发布）。

### 1.5 计数与统计口径（一条都不能错）

| 计数 | 删除进回收站 | 恢复 | 彻底删除 / 超期清理 |
| --- | --- | --- | --- |
| 标签 `use_count` | -1（若删前是 `1`） | +1（若恢复回 `1`） | **不再减**（已是 4，不在已发布集合内） |
| `publish_time` | 存入 `publish_time_before_delete` 后清空（沿用"非 1 状态为空串"约定） | 回填原值 | — |
| `view_count` / `like_count` / `favorite_count` / `comment_count` | **全部保留** | 原样（这就是"恢复"的意义） | 连带删除行与计数一起消失（帖子行没了，计数自然不存在） |
| 社区统计 `GET /forum/stats` | 不计入（只算 `status=1`） | 计入 | 不计入 |
| 用户发帖数 `postCount` | 不计入 | 计入 | 不计入 |
| 板块文章数（前台展示） | 不计入 | 计入 | 不计入 |
| 板块文章数（后台删除守卫） | **计入**（§0.4-L，全部状态口径） | 计入 | 不计入 |

## 2. 评论删除

### 2.1 语义：不留痕

- **物理删除**：直接 `DELETE FROM forum_comments WHERE id = ?`（不复用现有 `status=2` 软删路径）。
- **不留任何痕迹**：不写占位节点、不建审计表、不写日志表、不保留 `status=2` 行；前台删除后该评论**立即从列表消失**，`comment_count` 同步。
- 与后台软删**有意不对称**（§0.4-J）：后台抽屉里管理员删掉的评论仍保留行并显示"已删除"标记，用于纠纷追溯；作者删自己的话则真的拿走。

### 2.2 连带规则与计数（与第一阶段 §8-D15 ④ 同口径，只把"软删"换成"物理删"）

| 删除对象 | 连带 | `comment_count` |
| --- | --- | --- |
| 顶层评论 | 其下**全部回复行**（含他人回复）+ 上述所有评论的 `forum_comment_likes` 行 | 原子减 `1 + 回复数` |
| 单条回复 | 该回复的 `forum_comment_likes` 行 | 原子减 1 |

- 只删 `status=1` 的行；对已被后台软删（`status=2`）的评论再删 → **404**（对作者而言它本就不存在）。
- **不做**"删顶层时把他人回复挂到虚节点"这类花活——第一阶段的连带口径已被接受，本次只改落库方式。
- 不碰帖子的其它计数（`comment_count` 之外一律不动）。
- 删除自己的评论后，别人对它的点赞记录一并消失（计数行本身就没了，不会出现"计数 > 行数"的漂移）。

### 2.3 权限边界

| 主体 | 能做什么 |
| --- | --- |
| 评论作者 | 删自己的顶层评论与回复（主站新接口） |
| 楼主（文章作者） | **不能**删他人评论（本阶段不引入版主/楼主治理权） |
| 管理员 | 后台评论抽屉删任意评论（**软删**，保持现状） |
| 被禁言用户 | 仍可删自己的评论与帖子（§0.4-K） |
| 未登录 | 401（接口要求登录） |

## 6. 关键技术决策

| # | 决策 | 结论与理由 |
| --- | --- | --- |
| **D1** | 回收站用新状态还是复用 3 | **新增 `status=4`**。复用 3 会让"管理员下架"与"作者删除"继续混在一个状态里（现在靠 `remove_by` 区分，且 `remove_by='author'` 还能编辑重提），回收站的"可恢复/不可编辑/超期清理"三件事都需要独立语义。代价：状态枚举 +4 处文案同步（已列清单） |
| **D2** | 恢复是否重走审核 | **不重走**。回收站是"撤销删除"，内容零改动，与 §8-D13"编辑 = 重走审核"不冲突（那条约束的是**内容变更**）。删前是待审核/已驳回的，恢复后仍是待审核/已驳回 |
| **D3** | 恢复的 `publish_time` | **回填删除前的值**（新列 `publish_time_before_delete`）。否则"删除→恢复"零成本刷榜单（编辑重提要过审，没这个漏洞）。存量帖该列为空时兜底为当前时间 |
| **D4** | 回收站帖的可见性 | **公开接口全部 404（含作者）**，回收站列表单独取数据、不提供正文预览。理由：`_can_view_article` 被点赞/收藏/评论接口共用，若为作者放行 `status=4`，作者就能继续给"已删除"的帖子点赞评论，得再补 4 处 `status==1` 守卫；不如一开始就不放行，代码面更小、心智更清楚 |
| **D5** | 30 天与清理 | `deleted_at` 权威 + 接口自校验 + 列表过滤 + CLI 兜底（§1.3）。**不依赖 crontab 保证正确性**，与员工名片 `valid_to` 同款；不做"请求时顺带清理"（读路径不写库） |
| **D6** | 标签 `use_count` | 不新增规则：继续只由 `_set_article_status()` 在"进入/离开 `status=1`"时增减；彻底删除时因已是 4 而**不会重复扣减**（现有 `_cascade_delete_article` 已按 `status==1` 判断，天然正确） |
| **D7** | 评论"不留痕"的实现 | **物理删除行**，不写占位、不建审计表。与后台软删**有意不对称**：后台要留治理痕迹，作者要的是"我的话我拿走"。该不对称必须写进 `forum.py` 注释与 `AGENTS.md`，否则后人很容易"顺手统一"成一种 |
| **D8** | 删顶层评论连带他人回复 | **保留第一阶段 §8-D15 ④ 的连带口径**（连带物理删除）。代价是他人回复会随之消失；因为评论删除**不做二次确认**（D14），前端要保证"删顶层"这个按钮不至于被误点（次要文字样式、不做 hover 显隐）。新增"不能删"的例外规则会让删除语义变复杂，第一阶段明确接受 |
| **D9** | 清理 CLI 的 import 代价 | 新建轻量模块 **`backend/app/forum_core.py`**（纯 SQLAlchemy，不 import FastAPI/pydantic），承载 `RECYCLE_DAYS` / `purge_due()` / `cascade_delete_article()`；`app/forum.py` 从它 import 并 re-export。理由见 `app/staff_core.py` 头注释的生产实测：`app.staff`（完整 APIRouter）冷 import 实测 33s、内存紧张时分钟级——**`forum.py`（96KB、2294 行、全部 pydantic 模型）只会更慢**，CLI 绝不能 import 它 |
| **D10** | 禁言用户删自己的内容 | **允许**，不调 `_ensure_not_muted()`。删除不产生新内容，与"禁言期间点赞/收藏仍可用"同属有意例外 |
| **D11** | 并发与幂等 | 删除 / 恢复 / 彻底删除各自**单事务 + 状态前置校验**：重复点击第二次自然拿到 400/404，不会产生"删两次扣两次标签计数"。沿用论坛既有硬要求：`NullPool` 每请求一条连接、计数一律原子 SQL、禁止 read-modify-write（AGENTS.md 论坛规约） |
| **D12** | 图片与文件 | 彻底删除 / 超期清理**不动 `uploads/forum/` 下的文件**（第三阶段图床清理）。因此"删帖"不是"清空存储"，别当缺陷修 |
| **D13** | 回收站帖与板块删除 | 后台板块删除守卫继续按**全部状态**计数（回收站帖算"有文章"），宁可挡住删除也不留孤儿帖。这条是**有意为之**，UI 提示里不要写"板块为空" |
| **D14** | **评论删除不做二次确认（✅ 2026-10-05 Floyd 明确）** | 点击「删除」即发请求，**不弹确认框**（§3.4）。**代价**：误触不可恢复，且删顶层评论会连带他人回复一起消失。**缓解**：按钮保持与「赞 / 回复」同排的次要文字样式，不做大号危险按钮、不做 hover 显隐（移动端常驻可见、位置固定，避免"想点回复点到删除"）。**反向要求**：回收站页里的物理删**必须**二次确认（§3.2）——删帖一次性带走正文 + 全部评论/点赞/收藏，范围远大于一条评论，两者不对称是刻意的，不要在实现时"顺手统一" |

## 7. 项目规约与落地约束（防踩坑）

1. **契约三处同步**：`frontend/src/api/api.js`（`forumAPI`）、`admin-frontend/src/api/forum.ts`、后端 `app/forum.py` 的路由清单注释——新增接口必须三处齐全（AGENTS.md §API 契约 3）。
2. **状态枚举以 `ARTICLE_STATUS_TEXT` 为唯一权威**，前端 5 处文案表（§3.5）同步；不要在任何地方写"4 等于已删除"之外的猜测文案。**保留期天数同理**：前端只显示接口下发的 `recycleDays`，不要在页面里硬编码 30。
3. **不要绕开 `_set_article_status()` 改 `article.status`**（标签计数漂移的唯一来源）。
4. **时间**：一律 `String(30)` 北京时间 ISO；30 天比较用后端 `datetime` 计算后落库/下发，**前端不自己算剩余天数**（`daysLeft` 由后端给）。
5. 主站 HTTP 走 `axiosInstance`（已解包 `{code,message,data}`，页面里**不要判 `code`**）；错误直接 `ElMessage` / `showForumToast` 用 `e.message`。
6. 复用既有组件，别新造：`components/forum/ConfirmDialog.vue`（**帖子删除、回收站物理删**的确认弹窗既定位置；**评论删除不走它**，见 §3.4）、`ForumToast.vue`。
7. 新增前端组件一律独立 `.vue` SFC（本项目**不支持字符串 template**，AGENTS.md 论坛规约）。
8. 评论区新增的删除按钮：**共用样式类写在 `CommentSection.vue` 的非 scoped `<style>`**（`.cmt-act` 等已在那里，回复框是子组件、拿不到 scoped 样式）。
9. **必跑 `backend/forum_smoke_test.py`**（现有 176 项断言不许回归），并在其中新增本需求的断言（§8 的 1–9 条尽量都进冒烟）。
10. 迁移函数必须**幂等**（`PRAGMA table_info` 判存在），且放在 `init_db()` 的 `migrate_*` 序列里。
11. `main.py` 启动兜底的清理必须 try/except 包裹，**失败不阻断启动**。
12. 文档同步（与代码同批提交）：`AGENTS.md`（论坛规约：新增状态 4、回收站口径、评论删除不对称、CLI）、`README.md`（接口表 + 我的文章页说明 + 回收站页面）、`TODO.md`（移除"评论作者自删"顺延项，保留"评论编辑"）、第一阶段 PRD（§8-D16 与 §12.1 标注"已被本 PRD 取代"，修订记录加 v1.5 一行）。
13. **新增路由必须登记**：`/forum/recycle` 要在 `frontend/src/router/index.js` 里紧挨 `/forum/my` 写上（`meta.title: '已删除文章'`）；**不要**引入 `meta.hideNav` 之类的按路由隐藏导航机制——全站统一 `NavBar` 是既有规约。

## 8. 验收清单

**帖子（回收站）**

1. 作者删已发布帖 → 社区列表/详情/搜索均不可见、`GET /articles/{id}` 404、标签 `use_count` -1、该帖出现在 `/forum/recycle` 且显示"剩余 30 天"、`deletedAt` 正确。
2. 恢复 → 回到 `status=1`、`publish_time` 与删除前**完全一致**（不被顶到列表最前）、标签 `use_count` +1、浏览/点赞/收藏/评论数与删除前一致。
3. 删除"待审核"帖 → 回收站；恢复 → 回到 `status=0`（不是 1）；删除"已驳回"帖 → 恢复回 `status=2`。
4. 超期：手工把 `deleted_at` 改成 31 天前 → 恢复接口 410、回收站页面不显示该帖；跑 `forum_purge.py --dry-run` 报 1 条、实跑后行消失，且 `forum_comments` / `forum_comment_likes` / `forum_article_likes` / `forum_article_favorites` / `forum_article_tags` **无孤儿行**。
5. 彻底删除 → 立即物理删除 + 同样级联无孤儿；再次恢复 → 404。
6. 管理员下架帖（`status=3, remove_by='admin'`）→ 作者删除 **400**；已下架行在"我的文章"里**不显示**删除按钮。
7. 越权与幂等：删他人帖 404；删不存在 404；对已在回收站的帖子再删 400；**6 并发**双击删除/恢复不出 500、`use_count` 与实际引用数一致。
8. 可见性封锁：回收站帖的点赞 / 收藏 / 评论 / 浏览 接口**全部 404**（作者本人调用也一样）。
9. 后台：状态筛「回收站」能筛出该帖；「恢复」生效且状态回到 `statusBeforeDelete`；「删除」仍是不可恢复硬删；对回收站帖不显示通过/驳回/下架/置顶/加精。

**评论**

10. 作者删自己的**顶层评论**（下挂 2 条回复，其中 1 条是他人发的）：**点「删除」即生效、不出现任何确认弹窗** → 3 行全部物理消失、对应 `forum_comment_likes` 行清空、`comment_count` 减 3、列表无占位、详情页头部"评论 N"即时更新。
11. 作者删自己的**单条回复**（同样**无确认弹窗**）→ 只减 1，顶层评论与其它回复不受影响。
12. 删他人评论 404；未登录 401；已被后台软删（`status=2`）的评论再删 404。
13. 禁言中的用户删自己的评论与帖子 → 成功（不返回 403）。
14. 后台评论抽屉行为不变：管理员删评论仍是软删、仍显示"已删除"标记、仍连带回复、计数正确。

**回收站页面（新增页，§3.2）**

15. 我的文章页出现「查看已删除文章」按钮 → 点进 `/forum/recycle`；**未登录**直接访问该路由 → 跳登录页；浏览器直接输入 URL 可直达（前端 history 路由 + 生产 nginx 兜底均已有）。
16. 页面顶部**常驻保留期提示**，天数与接口下发的 `recycleDays` 一致（把后端 `RECYCLE_DAYS` 改成 15 后刷新：提示文案与"剩余 N 天"同步变化，前端零改动）。
17. 列表每行显示 标题 / 板块 / 删除时间 / 剩余 N 天 / 删除前状态；`daysLeft = 0` 显示「今天到期」；列表为空时显示空状态（含"保留 30 天"说明）。
18. 行内**「删除」= 物理删 + 二次确认**：点「删除」先弹确认框（文案写明"无法恢复"），**点"取消"不发任何请求、该行仍在**；点"确认"后该行消失，且该帖的评论 / 评论点赞 / 帖子点赞 / 收藏 / 标签关联行**已全部清空**；行内**「恢复」**执行后该行消失且帖子回到删除前状态（与验收 1–3 一致）。
19. 移动端（≤768px）：该页标题、`剩余 N 天`、`删除时间`、两个操作按钮不挤成一行、不横向滚动；详情页删除按钮可点、确认弹窗不溢出；评论区删除按钮在窄屏可点（无 hover 依赖）。

**文案与回归**

20. 文案：5 处状态标签都出现「回收站」且与后端 `statusText` 一致；删除确认文案已换成回收站口径（不再出现"你可以自行重新提交"）。
21. **对照验收（防"顺手统一"）**：同一轮里两条必须同时成立——**评论删除无确认弹窗**（验收 10/11）与**回收站删除有确认弹窗**（验收 18）。
22. 回归：`python3 forum_smoke_test.py` 全绿（既有 176 项 + 本次新增断言）。
