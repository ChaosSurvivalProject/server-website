### 0.2 第一阶段范围（MVP 边界）

**一句话目标**：跑通「内容消费 → 内容生产 → 互动反馈 → 后台管理」的最小业务闭环。

**范围内**：

| # | 模块    | 内容                                                        |
| - | ----- | --------------------------------------------------------- |
| 1 | 社区首页  | 双栏布局、Banner、板块标签栏、帖子列表（含置顶/精华标签、缩略图）、右侧三卡                 |

## 1. 目标与成功判据

### 1.1 目标

让一名已注册玩家可以：**在社区首页浏览帖子 → 点进详情读完 → 点赞/收藏/评论 → 自己发一篇帖 → 等管理员审核后出现在列表**；同时让管理员可以：**审核/置顶/加精/下架帖子、维护板块与标签、处置违规用户、配置首页 Banner**。

### 1.2 成功判据（第一阶段完成即成立）

1. 匿名用户可浏览板块、排序、搜索、翻页，可读完整文章与评论；
2. 登录用户可发帖（含 1 张封面 + 正文内嵌图）、点赞、收藏、评论；
3. 未登录用户点击发帖/点赞/评论均被引导至登录，**不出现跨页丢失编辑内容**（编辑草稿本地暂存，见 §5.3.4）；
4. 投稿进入待审核状态，管理员通过后出现在列表；驳回带理由且作者在「我的文章」可见；
5. 作者可编辑自己的文章，**保存后立刻退出公开列表并回到待审核**；管理员重新审核通过后恢复公开，且浏览量 / 点赞 / 收藏 / 评论**不因编辑而清零**；
6. 被禁言的用户发帖/评论返回明确错误提示（非 500、非静默失败）；
7. 首页右侧「文章数 / 浏览数 / 标签数」与数据库实时一致；
8. 全部页面在手机端（≤768px）可用，不出现横向滚动或文字溢出。

### 3.1 主站（frontend，history 路由，:5173）

## 4. 数据模型

全部模型写在 `backend/app/database.py`（本项目规约：无 `models/` 包）。库内 snake_case；对外 JSON camelCase（Pydantic v2 `alias` + `populate_by_name=True`）；时间列统一 `String(30)` 存北京时间 ISO 字符串，用 `app.crud._TZ`。

> **建表方式**：全部为**新表**，`Base.metadata.create_all` 自动建，**不需要写 `migrate_*` 补列函数**。  
> **唯一例外**：`users` 表需补 `mute_until` 列 —— 这是**存量表**，必须按既有先例（`migrate_user_extra_columns()`）追加一个幂等的 `ALTER TABLE` 迁移函数，并在 `init_db()` 末尾调用。

### 4.3 `forum_articles` 文章

| 字段                        | 类型       | 说明                                       |
| ------------------------- | -------- | ---------------------------------------- |
| id                        | 整数       | 主键                                       |
| category_id               | 整数       | 所属板块（**不允许**指向系统板块，见 §6.2.3）             |
| title                     | 字符串(255) | 标题                                       |
| content                   | 文本       | Markdown 源码（原样入库，渲染全在前端）                 |
| content_type              | 字符串(20)  | 固定 `'markdown'`（为第三阶段富文本预留，第一阶段后端不校验其它值） |
| summary                   | 字符串(255) | 摘要，后端从正文自动生成（见 §8-D2）                    |
| cover_url                 | 字符串(512) | 封面相对 URL，可空                              |
| author_id                 | 整数       | 作者 `users.id`，索引                         |
| status                    | 整数       | **0=待审核, 1=已发布, 2=已驳回, 3=已下架**           |
| review_note               | 字符串(255) | 驳回理由 / 下架原因（可空）                          |
| is_top                    | 整数       | 1=置顶                                     |
| is_featured               | 整数       | 1=精华                                     |
| view_count                | 整数       | 浏览量（冗余计数）                                |
| like_count                | 整数       | 点赞数（冗余计数）                                |
| favorite_count            | 整数       | 收藏数（冗余计数）                                |
| comment_count             | 整数       | 评论数（冗余计数）                                |
| publish_time              | 字符串(30)  | 发布（审核通过）时间；**非 `1 已发布` 状态时为空串**
| remove_by | 字符串(16) | 记录**是谁把文章移出公开**：`''`（未移除）/ `'author'`（作者自删）/ `'admin'`（管理员下架）；**决定作者能否编辑重提**（见下方状态机） |
| resubmit_count | 整数 | 编辑重提次数（默认 0）；后台审核列表据此区分"新投稿"与"老帖重提" |
| create_time / update_time | 字符串(30)  | —                                        |

> **状态机（第一阶段完整版）**：
>
> ```
> 新投稿                     ──▶ 0 待审核
> 0 待审核  ──(管理员通过)──▶ 1 已发布      [写 publish_time]
> 0 待审核  ──(管理员驳回)──▶ 2 已驳回      [review_note 存理由]
> 1 已发布  ──(管理员下架)──▶ 3 已下架      [remove_by='admin']
> 1 已发布  ──(作者自删)────▶ 3 已下架      [remove_by='author']
> 3 已下架  ──(管理员恢复)──▶ 1 已发布      [remove_by=''，不重新审核]
> 任意状态  ──(作者编辑保存)─▶ 0 待审核      [清空 review_note / publish_time / remove_by；resubmit_count +1]
> ```
>
> **作者编辑的准入范围**：`0 待审核` / `1 已发布` / `2 已驳回` / `3 已下架且 remove_by='author'`；
> **`3 已下架且 remove_by='admin'` 不允许作者编辑**（否则可用"编辑重提"绕过管理员下架）
>
> | 起始状态 | 触发 | 结果 | 备注 |
> |---|---|---|---|
> | — | 登录用户投稿 | `0 待审核` | `publish_time=''` |
> | `0` | 管理员通过 | `1 已发布`，**重写** `publish_time` | 标签 `use_count` +1 |
> | `0` | 管理员驳回（须填理由） | `2 已驳回` | `review_note` 存理由 |
> | `1` | 管理员下架 | `3 已下架`，`remove_by='admin'` | 标签 `use_count` -1 |
> | `1` | 作者自删 | `3 已下架`，`remove_by='author'` | 标签 `use_count` -1 |
> | `3` | 管理员恢复 | `1 已发布`，`remove_by=''` | 内容未变，**不重新审核**；`publish_time` 重写 |
> | **`0` / `1` / `2` / `3`（`remove_by='author'`）** | **作者编辑保存** | **`0 待审核`**，`remove_by=''`，`review_note=''`，`publish_time=''`，`resubmit_count` +1 | 若原状态为 `1`，同时标签 `use_count` -1（见 §8-D8）；**点赞 / 收藏 / 评论 / 浏览量全部保留** |
> | `3`（`remove_by='admin'`） | 作者尝试编辑 | **400**，提示"该帖已被管理员下架，请联系管理员处理" | 防止用编辑重提绕过管理员下架 |
> | `1` | 管理员后台改属性（§6.1.3） | 状态**不变** | 管理员本人即审核者，改板块/标签/封面无需重新走审核 |
>
> **三条硬规则**：
> 1. 作者编辑 = **重走审核**，不存在"改了立刻生效"的路径；
> 2. 编辑保存会**清空上次的 `review_note`**（旧理由已失效），但进入编辑页时先把原理由展示给作者看（§5.3.3），避免"理由还没看清就没了"；
> 3. `publish_time` 在每次进入 `1 已发布` 时**重写为新时间**，因此重提通过的老帖会按发布时间排到列表最前。这是**预期行为**（重提即重新发布），审核成本（每次都要人工过）本身就是对滥用的天然约束。

### 4.4 `forum_comments` 评论

| 字段          | 类型      | 说明                                   |
| ----------- | ------- | ------------------------------------ |
| id          | 整数      | 主键                                   |
| article_id  | 整数      | 所属文章，索引                              |
| author_id   | 整数      | 评论人 `users.id`                       |
| content     | 文本      | 纯文本（**不接受 Markdown 与 HTML**，见 §8-D5） |
| parent_id   | 整数      | **0 = 顶层评论；非 0 = 所属顶层评论的 id**（楼中楼只做两级，见 §8-D15） |
| reply_to_user_id | 整数 | 被回复者 `users.id`，可空。仅用于在回复上显示"回复 @某人"；**回复的回复仍挂同一个顶层评论** |
| status      | 整数      | 1=正常, 2=已删除（软删，不出现在列表，计数同步递减）        |
| like_count  | 整数      | 点赞数（冗余计数；评论点赞见 §4.5.3）              |
| create_time | 字符串(30) | —                                    |

> **两级楼中楼规则**（完整规则见 §8-D15）：`parent_id` **只指向顶层评论**。对某条回复再回复时，`parent_id` 仍填这条回复所属的顶层评论 id，另用 `reply_to_user_id` 记录"回复给谁"。**不引入第三级及更深嵌套**——否则渲染、分页与删除连带都会失控。
>
> **排序与计数口径**：
> - 顶层评论**按时间倒序**（最新在前）；同一顶层评论下的回复**按时间正序**（先来后到，符合对话直觉）；
> - 文章 `comment_count` = **顶层评论数 + 回复数**（回复也算评论，与详情页"评论 N"的直觉一致，不另设"回复数"字段）。
>
> **删除连带**：删除顶层评论 → 其下所有回复**一并软删**，`comment_count` 减去 `1 + 回复数`；删除单条回复 → 只减 1。两者的评论点赞行同步删除（§4.5.3）。

## 5. 前端功能需求

> **视觉基调**：浅色主题，与官网首页一致；复用已有背景图；主内容 70% + 侧边栏 30%，整体居中并留边距。  
> **抽象要求**：帖子卡片、侧边栏用户卡、评论区必须抽成独立组件放在 `frontend/src/components/forum/`，仅靠 props 驱动，供后续阶段直接扩展。

### 5.1 顶部导航栏（`NavBar.vue` 改造）

| #  | 需求                         | 落地                                     |
| -- | -------------------------- | -------------------------------------- |
| N1 | 复用现有导航栏组件                  | 不新建导航组件                                |
| N2 | 头像**左侧**新增站内信按钮（通知图标 bell） | 仅已登录时显示；点击弹出提示"站内信功能开发中"，**不跳转、不请求接口** |
| N3 | 新增「社区」入口 → `/forum`        | PC 端与移动端菜单同步                           |
| N4 | 未读数角标                      | **不做**（第二阶段随站内信一起做），不留假角标              |

### 5.2 社区首页 `/forum`

#### 5.2.1 Banner 区

- 圆角矩形大卡片，高度建议 180–220px（桌面端）；
- **左侧**：主标题 `星穹旅驿站` 社区（取自 `bannerTitle`）+ 下方小字副标题（取自 `bannerSubtitle`）；
- **右侧**：MC 人物 + 城堡插画。**素材待提供**：未配置 `bannerImage` 时渲染项目内置占位图（CSS 渐变 + 文字提示），**不得**外链第三方图床；
- **右下角**横向排布三项：
  1. **排序下拉**（按发布时间 / 按访问量 / 按回复数）→ 写入 query `sort`，切换即不刷新重取；
  2. **搜索框** → 占位文案取 `searchPlaceholder`；回车触发查询，写入 query `q` 并重置 `page=1`；支持清空；
  3. **发布文章按钮** → `/forum/new`；未登录点击跳 `/login?redirect=/forum/new`。

#### 5.2.2 分类标签导航

- 横向排列，顺序按 `sortOrder` 升序；`isHidden=1` 的板块不渲染；
- 每项前有彩色小圆点（`color`），当前选中项高亮；
- 点击写入 query `category=<code>` 并重置 `page=1`；
- 「首页」为默认选中项；「推荐」按 §0.3-D 口径；
- 移动端允许横向滚动，不换行挤压。

#### 5.2.3 帖子列表

- 垂直卡片式列表，一页 12 条，底部翻页器；
- 每张卡片自上而下：
  - **顶部标签栏**：`置顶`（红）/ `精华`（橙）+ 所属板块标签（用板块色）；无则不渲染该行；
  - **标题**：加粗，点击进入 `/forum/post/:id`；
  - **摘要**：灰色，单行省略（CSS `-webkit-line-clamp: 2`）；
  - **底部信息栏**：左＝作者头像 + 昵称 + 徽章 + 发布时间（相对时间：刚刚/N 分钟前/N 小时前/MM-DD）；右＝浏览 / 点赞 / 评论三个图标 + 数字；
  - **缩略图**：右侧方形（建议 96×96，圆角），`coverUrl` 优先，其次正文首图，都没有则不渲染该位；
- **空状态**：筛选无结果时展示"这里还没有帖子" + 「发布第一篇」按钮（未登录时跳登录）；
- **排序**：`latest` 按 `publish_time` 倒序；`views` 按 `view_count` 倒序；`comments` 按 `comment_count` 倒序。**置顶帖永远排在非置顶帖之前**（三档排序都生效）。

#### 5.2.4 右侧边栏

| 卡片      | 内容                                                  | 数据来源                                                              |
| ------- | --------------------------------------------------- | ----------------------------------------------------------------- |
| 用户个人信息卡 | 头像、昵称、等级标签、`我的文章`（→`/forum/my`）、`头衔管理`（点击提示"功能开发中"） | 已登录：`/api/auth/me` + `/api/forum/my/stats`；**未登录**：改为"登录 / 注册"引导卡 |
| 社区统计卡   | 三列：文章数 / 浏览数 / 标签数                                  | `GET /api/forum/stats`（实时聚合，见 §6.4.3）                             |
| 热门标签卡   | 标签云，显示 `# 标签名 + 计数`                                 | `GET /api/forum/tags/hot?limit=20`；点击写入 query `tag=<name>`        |

> 依据文档写"热门标签卡（静态数据即可）"，但既有接口成本为零，**直接接真数据**，不做假数据。

### 5.3 发布 / 编辑文章页 `/forum/new` · `/forum/edit/:id`

> **两路由复用同一页面组件**（`mode = 'create' | 'edit'`），表单字段、校验、编辑器、上传通道完全一致，差异只在标题文案、初始值来源、提交接口与顶部提示条。

- 左上角 `← 返回社区`，返回 `/forum`；页面**不挂全局导航**（专注写作，与详情页一致）；
- 表单字段：

| 字段   | 控件                            |  必填 | 校验                                                            |
| ---- | ----------------------------- | :-: | ------------------------------------------------------------- |
| 选择板块 | 平铺卡片选择（6 个普通板块，带色点）           |  ✅  | 未选则提交按钮禁用 + 提示"请选择板块"                                         |
| 标题   | 单行输入                          |  ✅  | 2–100 字（前端拦 + 后端复校）                                           |
| 封面   | 上传（单张，可预览可删除）                 |  ❌  | png/jpg/jpeg/gif/webp，≤5MB；上传走 `POST /api/forum/upload/image` |
| 正文   | Markdown 编辑器（编辑 / 预览切换 + 工具栏） |  ✅  | 10–50000 字                                                    |
| 标签   | 标签输入（回车确认）                    |  ❌  | 单个 ≤20 字；**最多 5 个**；超过 5 个时输入框禁用并提示；下拉展示已有标签供选择               |

- **提交按钮文案**：`create` 模式 → `提交审核`（明示"提交后需管理员审核通过才会公开"）；`edit` 模式 → `保存并重新提交审核`；
- `create` 成功：跳 `/forum/my` 并提示"已提交，等待审核"；
- `edit` 成功：跳 `/forum/my` 并提示"已重新提交，等待审核"。

#### 5.3.1 Markdown 编辑器

- 主站新增依赖 **`md-editor-v3`**（与后台同款 `^7.0.0`，保证预览效果一致）；
- 渲染预览**必须**走 `frontend/src/utils/markdown.js` 的既有管线，**不得**另写一套渲染入口（AGENTS.md 红线）；
- 该文件现导出 `renderAnnouncementContent(content, contentType)`，实施时**泛化命名**为 `renderMarkdownContent(content)`，**保留旧导出名作为别名**（公告详情页正在用），避免回归。

#### 5.3.2 正文内嵌图片

- 编辑器粘贴 / 拖拽 / 上传的图片一律走 `POST /api/forum/upload/image`；
- 插入正文的 URL 为 `![alt](/api/announcement/uploads/forum/YYYYMM/xxx.png)`；
- **禁止**外链第三方图床（与项目"不依赖第三方平台"的既有取向一致）。

#### 5.3.3 编辑模式（`/forum/edit/:id`）

**进入条件**（任一不满足即按 404 处理，不暴露文章是否存在）：

| 条件 | 处理 |
|---|---|
| 未登录 | 跳 `/login?redirect=/forum/edit/:id` |
| 文章不存在 / 已硬删 | 404 |
| 当前用户 ≠ 作者，且非管理员 | 404 |
| `status=3` 且 `remove_by='admin'` | **400 页面提示**"该帖已被管理员下架，请联系管理员处理"（不渲染编辑表单） |
| `status=0 / 1 / 2`，或 `status=3` 且 `remove_by='author'` | 正常进入编辑表单 |

**页面顶部提示条**（按原状态给不同文案，醒目且不可关闭）：

| 原状态 | 提示文案 |
|---|---|
| `0 待审核` | 「该帖正在审核中。保存后将重新提交审核。」 |
| `1 已发布` | 「该帖已发布。保存后将**重新进入审核，通过前会暂时从社区隐藏**；期间的浏览 / 点赞 / 收藏 / 评论都会保留。」 |
| `2 已驳回` | 「该帖未通过审核：**<驳回理由>**。修改后可重新提交，保存后原驳回理由将被清除。」 |
| `3 已下架`（作者自删） | 「该帖已被你删除。保存后将重新提交审核。」 |

**其它行为**：

- 表单预填该文章现有的板块、标题、封面、正文、标签（标签可增删，仍受 5 个上限约束）；
- **不预填**任何编辑历史——第一阶段不做版本记录（§12.1）；
- 保存成功后清空对应草稿；编辑模式草稿键为 `forum:draft:edit:<id>`，与新建页的 `forum:draft` **分离**（见 §5.3.4）；
- 提交后文章状态一律变为 `0 待审核`（规则见 §4.3 状态机、§8-D13）。

#### 5.3.4 草稿暂存（防丢失）

- 表单内容变化时写入 `localStorage`：`create` 模式键 `forum:draft`，`edit` 模式键 `forum:draft:edit:<id>`（**两者分离**，避免新建页与编辑页互相覆盖）；
- 进入对应页面时若检测到所属草稿，顶部提示"发现未提交的草稿，是否恢复？"（恢复 / 丢弃）；
- 提交成功后清空对应草稿；
- **不做**服务端草稿（第二阶段候选）。

### 5.4 文章详情页 `/forum/post/:id`

#### 5.4.1 顶部导航

- 左上角**只有** `← 返回社区`（返回 `/forum`，若从列表带 query 进入则回退到带 query 的地址），无其他全局导航。

#### 5.4.2 帖子详情卡片

- **头部元数据**：板块标签（板块色）→ 标题（H1 级视觉）；
- **作者与统计**：左＝头像 + 昵称 + 徽章 + `发布于 MM-DD`；右＝浏览量 / 点赞量 / 评论量三项；
- **正文**：Markdown 渲染（代码高亮 + 图片自适应：`max-width: 100%`；表格横向可滚）；代码块顶栏语言标签 + 复制按钮（复用既有 CSS 与事件委托方案）；
- **底部操作栏**（三个圆角矩形按钮）：
  - `赞 N`：已登录点击 → 调 `POST /api/forum/articles/{id}/like`，**切换**样式（已赞高亮）与计数；未登录 → 跳登录；
  - `收藏`：同上，走 `/favorite`；已收藏态显示"已收藏"；
  - `分享`：优先 `navigator.share`（移动端），降级为复制当前 URL + 提示"链接已复制"，**无后端接口**；
- **不可见情形**：
  - 文章不存在 / 已硬删 → 404 文案"帖子不存在或已被删除"；
  - `status=0 待审核` 或 `2 已驳回`：**仅作者本人与管理员**可见，页顶显示醒目横幅"该帖正在审核中" / "该帖未通过审核：<理由>"；其他访客一律按 404 处理；
  - `status=3 已下架`：作者与管理员可见并展示"已下架"横幅，其他访客 404。
- **作者操作入口**：仅当「当前登录用户 == 作者」且状态在可编辑准入范围内（§4.3）时，在作者信息行右侧渲染一个次要样式 `编辑` 按钮 → `/forum/edit/:id`；非作者一律不渲染（前端隐藏只是体验，后端仍独立校验，见 §9-13）。

#### 5.4.3 评论区卡片

**标题**：`评论 N` —— N = **顶层评论数 + 回复数**（口径见 §4.4）。

**输入区（发表顶层评论）**：左侧当前用户头像（未登录显示默认头像）；右侧多行文本框（占位符"友善地发表你的看法..."）；下方灰色提示"理性发言，文明交流"；右下角**蓝色**`发表评论`按钮（未登录时点击跳登录，文本框不可编辑并提示"登录后参与讨论"）。非空校验（1–500 字），成功后清空输入框、列表顶部插入新评论、`评论 N` 计数 +1。

**列表结构：两级楼中楼**

- **顶层评论**：头像 + 昵称 + 徽章 + 时间 + 内容（纯文本，换行保留）；
  - 底部操作行：`赞 N` · `回复`；
  - **按时间倒序**（最新在前），分页 10 条/页；
  - 其下若有回复，以**缩进列表**展示（左侧一条细竖线），**按时间正序**；
- **回复项**：头像 + 昵称 + 徽章 + 时间 + 内容；若该回复是对某条回复的回复，内容前显示灰色小字 `回复 @昵称`（**纯展示，不可点击**）；
  - 底部操作行同样是 `赞 N` · `回复`；
  - **回复不单独分页**：单条顶层评论下的回复一次性全部返回（社区规模下可接受；"超过 30 条折叠"留第二阶段）。

**回复交互（内联展开，不用弹窗）**

- 点击任意评论或回复的 `回复` → 在其**正下方**展开内联输入框；输入框左侧为当前用户头像，上方标注 `回复 @昵称` 与被回复内容摘要（单行省略），带 `取消` / `发表回复` 两个按钮；
- 同一时间**只允许展开一个回复框**（点其它回复则迁移过去）；
- 发表成功后：① 输入框收起；② 新回复插入到该顶层评论回复列表的**末尾**（正序）；③ `评论 N` 计数 +1；
- **回复不改变顶层评论排序**（不会把老评论顶上来）；
- 未登录点 `回复` → 引导登录，**不展开输入框**。

**评论点赞**

- 每条评论（顶层与回复**都**）右侧有 `赞 N`；已登录点击 → `POST /api/forum/comments/{id}/like`，**幂等切换**（已赞再点即取消），数字与高亮态同步更新；未登录 → 引导登录；
- 刷新后已赞状态保持（列表接口对已登录用户返回每条评论的 `liked`）。

**删除**

- **第一阶段评论区不提供删除入口**——评论治理统一由管理员在后台处置（§6.1.5）。"作者删除自己的评论"列第二阶段（§12.1）。

**空状态**：虚线框 + "还没有评论，来抢沙发吧~"。

#### 5.4.4 右侧边栏

| 卡片       | 内容                                                                             |
| -------- | ------------------------------------------------------------------------------ |
| 作者信息卡片   | 标题`作者`；大头像 + 昵称 + 徽章；横向三项数据 `发帖 / 获赞 / 粉丝`；下方两个并排按钮：蓝色 `+ 关注`、绿色 `打赏作者`（带金币图标） |
| 作者其他帖子卡片 | 标题`作者其他帖子`；该作者其他**已发布**文章列表（标题 + 浏览量），最多 5 条，点击跳详情；无则显示"暂无其他帖子"                |

- `+ 关注` 与 `打赏作者` 第一阶段均为**占位**：点击提示"功能后续开发"（§0.3-B / §0.3-E）；
- `粉丝` 恒显示 `0`（后端返回 0，前端不写死，避免第二阶段改两处）。

### 5.5 我的文章页 `/forum/my`（§0.3-F 的必要配套）

- 列表展示当前用户全部文章（各状态），每行：标题 / 板块 / 状态标签（待审核·已发布·已驳回·已下架）/ 浏览·点赞·评论 / **最近提交时间**（`updateTime`）/ 创建时间；
- 已驳回的行展示驳回理由；已下架的行展示下架原因（若有），并区分"你删除的"与"管理员下架"；
- 重提过的行显示 `第 N 次提交`（`resubmitCount > 1` 时）；
- **操作**：
  - `查看`（→ 详情页）；
  - `编辑`（→ `/forum/edit/:id`）——**`remove_by='admin'` 的已下架文章不显示此按钮**，改为灰字提示"管理员下架，请联系管理员"；
  - `删除`（软删，二次确认）；已下架的行不显示此按钮；
- 状态筛选（全部 / 待审核 / 已发布 / 已驳回 / 已下架）+ 分页。

> 依据文档未提此页，但没有它，被驳回的作者**永远看不到自己错在哪**，也无法编辑重提——审核机制的必要配套，成本约 1 个页面 + 1 个接口。

## 6. 后台功能需求（admin-frontend）

### 6.1 文章管理 `/forum/article/list`

#### 6.1.1 列表与检索

| 维度  | 支持                         |
| --- | -------------------------- |
| 关键词 | 标题模糊搜索                     |
| 作者  | 按昵称 / 账号模糊搜索（或下拉选人）        |
| 板块  | 下拉（含"未分区"？无此情况，板块必填）       |
| 标签  | 下拉选择（多选）                   |
| 状态  | 全部 / 待审核 / 已发布 / 已驳回 / 已下架 |

- 表格列：ID、标题、板块、标签、作者、状态、置顶、精华、浏览/点赞/评论、**提交次数**、**最近提交时间**、创建时间、操作；
  - **提交次数**（`resubmitCount`）：`0` 显示"首次投稿"，`≥1` 显示 `重提 N 次` 并加浅色标记——用于一眼区分"新投稿"与"老帖改稿重提"，避免审核员把重提的老帖当成新帖；
  - **最近提交时间**（`updateTime`）：待审核队列按它倒序更贴合审核直觉（谁刚提交谁在前）；
- 默认按 `create_time` 倒序；分页 10/20/50 可选。

#### 6.1.2 审核与操作

| 操作     | 行为                                                         | 约束                     |
| ------ | ---------------------------------------------------------- | ---------------------- |
| **通过** | `status: 0 → 1`，**重写** `publish_time`（始终取当前时间），并累加所涉标签 `use_count` | 仅待审核文章（含新投稿与老帖重提）      |
| **驳回** | `status: 0 → 2`，`review_note` 必填（1–200 字）                  | 仅待审核文章                 |
| **置顶** | 切换 `is_top`                                                | 幂等                     |
| **加精** | 切换 `is_featured`                                           | 幂等                     |
| **下架** | `status → 3`，`remove_by='admin'`，`review_note` 可填（显示给作者）      | 已发布/已驳回                |
| **恢复** | `status → 1`，`remove_by=''`，`publish_time` 重写                | 仅已下架                   |
| **删除** | **硬删除**：级联删除该文章的评论、点赞、收藏记录                                 | 二次确认弹窗明确"不可恢复，且评论一并删除" |
| 批量     | 批量通过 / 批量下架 / 批量删除                                         | 可选（若做，需二次确认）           |

- 审核动作需**二次确认**（通过/驳回除外可轻确认）；操作后列表**局部刷新**而非整页重载。
- ⚠️ **重提文章的审核注意点**：文章可能已被浏览 / 点赞 / 评论过，审核改状态**不影响**这些数据；但通过后它会因 `publish_time` 被重写而**排到列表最前**（§4.3 硬规则 3），这是预期行为，不是 bug。审核时请留意「提交次数」列，对反复重提的内容保持关注。

#### 6.1.3 属性修改

- 编辑抽屉/弹窗支持修改：所属**板块**、**标签**（≤5）、**封面图**（替换/清除）、**标题**；
- **正文只读预览**（Markdown 渲染效果），第一阶段不支持后台改正文——需要改内容时由**作者自行编辑重提**（§5.3.3），改动仍会过一遍审核，责任链清晰；
- 板块/标签变更时**同步维护** `forum_tags.use_count`（旧标签减、新标签加）。

#### 6.1.4 数据统计与预览

- 列表直接展示浏览量 / 点赞量 / 评论量；
- 「预览」按钮打开抽屉，用后台既有 Markdown 渲染（md-editor-v3 预览模式或 `marked`）**渲染全文**；
- 「查看原帖」跳主站 `/forum/post/:id`（新窗口）。

#### 6.1.5 评论抽屉（§0.3-A）

- 「评论数」可点，打开抽屉列出该文章**全部评论与回复**（含已删除标记）；回复按**缩进**展示并标注 `回复 @昵称`，与前台结构保持一致；
- 支持**删除单条评论**（软删 `status=2`）：
  - 删除**顶层评论** → 其下所有回复**一并软删**，删除前弹窗须明确提示"将同时删除该评论下的 N 条回复"；`comment_count` 减去 `1 + 回复数`；
  - 删除**单条回复** → 只减 1；
  - 两种情况都**同步删除对应的评论点赞行**（§4.5.3），不产生孤儿数据；
- 抽屉内**不提供**回复、点赞、置顶功能——管理员的处置口径是"只删不参与"，避免后台出现两套互动入口。

#### 6.1.6 封面图库

- 「封面图库」入口：列出 `uploads/forum/**` 下的图片文件（文件名/大小/上传时间/被引用次数）；
- 第一阶段**只读展示 + 复制 URL**；清理冗余文件归第三阶段。

### 6.2 板块管理 `/forum/category/list`

#### 6.2.1 分类维护

- 列表列：ID、名称、code、颜色、排序、是否隐藏、是否系统、文章数、操作；
- 新增：名称（唯一）+ code（小写字母数字，唯一，创建后不可改）+ 颜色（取色器）+ 排序；
- 编辑：名称、颜色、排序、是否隐藏；**系统板块不可改名称/code/删除**；
- 删除：**仅当该板块下无文章时允许**；有文章时提示"请先迁移或删除该板块下的 N 篇文章"（不提供级联删除文章，防误删）。

#### 6.2.2 视觉配置

- 颜色即首页彩色小圆点（前端直接消费 `color`）；
- 排序权重直接决定标签栏顺序。

#### 6.2.3 隐藏

- `is_hidden=1`：标签栏不显示，但已有文章仍可经直链访问；
- **禁止**把文章投稿到系统板块：后端在创建/修改文章时校验 `category.is_system=0`，否则 400。

### 6.3 标签管理 `/forum/tag/list`

| 功能     | 说明                                                                       |
| ------ | ------------------------------------------------------------------------ |
| 标签库    | 列表：ID、名称、使用数（`use_count`）、来源（system/user）、是否置热、创建时间                      |
| 来源筛选   | `user` 来源即"用户发帖时自动新建"的标签，**默认按此筛选作为清理入口**（需求原文："需要在后台进行审核或定期清理"）         |
| 重命名    | 修改标签名（判重）；重命名即为最常用的"清理"动作，`use_count` 不变                                 |
| **合并** | 选择目标标签，把源标签的引用全部迁移到目标，删除源标签，重算目标 `use_count`；弹窗明确"合并后源标签消失，N 篇文章将改挂目标标签" |
| 删除     | 允许删除任意标签；删除时从文章的标签关联中移除该标签，并回写受影响文章的 `update_time`                       |
| 置热     | 切换 `is_hot`；首页热门标签卡优先展示 `is_hot=1`，其余按 `use_count` 倒序补齐                  |
| 新增     | 后台可手工建标签（`source='system'`）                                              |

> **标签不与文章强绑定**：文章标签用独立关联表（`forum_article_tags`，见下），不用逗号串字段，否则合并/重命名/删除都会写坏数据。

### 6.4 社区配置 `/forum/config`

#### 6.4.1 Banner 配置

- 三个字段：标题（≤50）、副标题（≤100）、插画图（上传，可清除）；
- 上传走 `POST /api/announcement/upload/image`（管理员接口，后台可用）；
- 保存后首页即时生效（后端不做缓存）。

#### 6.4.2 交互配置

- 排序默认项：单选（按发布时间 / 按访问量 / 按回复数）→ `defaultSort`；
- 搜索框占位文案 → `searchPlaceholder`（≤30 字）。

#### 6.4.3 基础统计（只读）

- 页面顶部展示三项实时数据：**文章数**（`status=1` 的文章总数）、**浏览数**（`status=1` 的 `view_count` 之和）、**标签数**（被 `status=1` 文章引用的去重标签数，§0.3 口径）；
- **第一阶段不做手动修正**（需求原文的"手动修正"归第二阶段随自动化一起做），避免出现"手填了个错数还没人知道"；
- 统计与首页统计卡共用 `GET /api/forum/stats`。

### 6.5 用户管理扩展 `/user/list`

#### 6.5.1 禁言 / 解禁（§2 禁言语义）

- 列表新增列「禁言至」（空=未禁言，命中显示到期时间）；
- 行操作新增 `禁言`（弹窗选时长：1 天 / 3 天 / 7 天 / 30 天 / 永久）+ `解禁`；
- 后端：`PUT /api/auth/admin/users/{id}/mute`，body `{muteUntil: "YYYY-MM-DDTHH:MM:SS" | ""}`（空串=解禁）；
- 与既有 `status` 三态（正常/禁用/删除）**并存且正交**：禁用=不能登录，禁言=能登录不能发言。

#### 6.5.2 用户论坛数据

- 行操作 `论坛数据` → 弹窗展示：发帖数（`status=1`）、获赞数（该用户文章 `like_count` 之和）、粉丝数（恒 0，§0.3-B）、最近 5 篇帖子的标题与状态；
- 数据接口 `GET /api/forum/admin/user-stats/{userId}`。

#### 6.5.3 徽章（等级/头衔）

- 第一阶段**不建**等级与头衔体系（第二阶段）；
- 列表与前台作者徽章只区分：`role=admin` → 显示"管理员"徽章；`role=user` → 不显示徽章；
- 徽章样式在前端常量表内维护（`frontend/src/utils/forumBadges.js`，与后台保持同名同色），**不硬编码在多个组件里**；
- 依据文档示例中的"炽热行者""VIP"等**第一阶段不出现**，不得以假数据填充。

## 8. 关键技术决策

| #       | 决策             | 结论与理由                                                                                                                                                                                                                                                                                                             |
| ------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **D1**  | 普通用户上传图片       | **新增 `/api/forum/upload/image`（登录用户）**，不复用 `/api/announcement/upload/image`（后者是 `require_admin`，普通用户会 403）。落盘到 `<UPLOAD_DIR>/forum/YYYYMM/`，对外 URL 仍走 `/api/announcement/uploads/forum/...`——**复用同一个 StaticFiles 挂载，零 nginx 改动**是最大收益；代价是 URL 前缀带 `announcement` 字样（可接受，勿为此新增 StaticFiles 挂载点，那会引入新的 location 需求） |
| **D2**  | 摘要生成           | 后端从 Markdown 正文自动截取：剔除代码围栏、图片、链接语法、标题符号后取前 **100 字**（不足则全取），空正文兜底为空串。理由：依据文档的表单字段里**没有**摘要输入项，不该由用户填第二遍                                                                                                                                                                                                           |
| **D3**  | 搜索             | 第一阶段用 `title LIKE %q% OR summary LIKE %q%`（配合 SQLite `LIKE` 大小写不敏感默认行为）。**不使用 FTS5**：论坛正文检索属第三阶段，且 kb 的 FTS5 是 trigram 独立表方案，语义与排序都不同，硬套会引入两套全文索引维护成本                                                                                                                                                             |
| **D4**  | 浏览量计数          | 详情接口不计数；前端挂载后调 `POST /api/forum/articles/{id}/view`，后端执行 `UPDATE ... SET view_count = view_count + 1`（**原子自增，禁止 read-modify-write**，否则并发下计数丢失）。重复刷新会重复计数，**明确接受**（P2 再做去重）                                                                                                                                        |
| **D5**  | 评论体格式          | 评论**纯文本**入库，前端渲染时转义 + `white-space: pre-wrap`。评论**不走** Markdown 管线——否则要再引一套 sanitize 策略，且评论区是 XSS 最高频入口。**回复与顶层评论同规则**（回复体也不解析 Markdown）                                                                                                                                                                                                           |
| **D6**  | 冗余计数一致性        | `like_count` / `comment_count` / `favorite_count` / `view_count` 全部用原子 SQL 自增/自减，与关系表操作**在同一事务**内提交；点赞/收藏切换时先判存在再决定增或减，避免计数漂移。评论的 `forum_comments.like_count` 同理（评论点赞切换幂等）；`comment_count` 的增量为 1（新评论 / 新回复）或 `1 + 回复数`（删顶层评论），口径见 §8-D15                                                                                                                                                                                     |
| **D7**  | 标签关联           | 独立关联表 `forum_article_tags(article_id, tag_id)` + `(article_id, tag_id)` 唯一索引。理由见 §6.3 说明（合并/重命名/删除都要能安全改）                                                                                                                                                                                                         |
| **D8**  | `use_count` 维护 | 标签 `use_count` 定义为"被 `status=1` 文章引用数"，**只挂在"是否处于已发布状态"这一个转移点上**，规则唯一：① 任何**进入** `status=1` 的转移（审核通过、管理员恢复上架）→ 按文章**当期**标签集合各 +1；② 任何**离开** `status=1` 的转移（作者编辑重提、管理员下架、作者自删）以及**硬删除**一篇 `status=1` 的文章 → 按文章**当期**标签集合各 -1；③ 后台改标签（§6.1.3）按新旧集合差额增减（仅当文章 `status=1`）。标签合并/删除时对受影响文章**整体重算**。编辑重提**不会二次扣减**（`status=0` 时本就不在已发布集合内，重复编辑同样只扣一次）。**不做**定时重算（第二阶段候选），但每篇文章一旦改变状态必须同步更新                                                                                                                                                                       |
| **D9**  | 后台正文只读         | 后台**不提供**改正文能力（§6.1.3）——需要改内容时由作者自行编辑重提（D13），改动照样过审，责任链与留痕都清晰。审核是"通过/驳回"，不是"代笔改写"                                                                                                                                                                                                                                                                        |
| **D10** | 事务与并发          | SQLite 已开 WAL + `busy_timeout=8000`（`init_db`）。论坛写入频次高于公告，**仍按单 worker 部署**（与知识库限流同款前提）；若后续多 worker，需重新评估计数与限流方案                                                                                                                                                                                                  |
| **D11** | 时间与相对时间        | 后端只存/返 ISO 字符串；"N 分钟前"由前端 `src/utils/` 内新增的格式化函数计算，**不在后端算相对时间**                                                                                                                                                                                                                                                  |
| **D12** | 后台渲染           | 后台文章预览用 `md-editor-v3`（已有依赖 `^7.0.0`）的预览能力，**不引新依赖**                                                                                                                                                                                                                                                              |
| **D13** | **作者编辑 = 重新审核**（✅ 2026-09-27 拍板） | 作者可编辑自己的文章（字段与发布页完全一致：板块 / 标题 / 封面 / 正文 / 标签）。保存后文章的 `status` **一律回到 `0 待审核`**，并清空 `review_note`、`publish_time`、`remove_by`，`resubmit_count` +1；管理员重新审核通过前**不公开**。**保留**浏览量 / 点赞 / 收藏 / 评论（同一篇文章的修订，不是新文章，清零会让作者数据无故丢失）。准入范围与状态机见 §4.3；`remove_by='admin'` 的已下架帖**不允许**作者编辑（否则等于绕过管理员下架）。副作用：重提通过的老帖会因 `publish_time` 重写而排到列表最前——预期行为，且每次编辑都要人工过审，滥用成本足够高 |
| **D14** | 作者与管理员改东西的区别 | **作者改任何内容 → 重新审核**；**管理员在后台改板块/标签/封面/标题 → 状态不变**（管理员本人即审核者，§6.1.3）。两者能力并存、互不覆盖，实现时不要顺手把管理员改属性也踢回待审核 |
| **D15** | **评论：两级楼中楼 + 点赞**（✅ 2026-09-27 追加纳入第一阶段） | ① **只做两级**：`parent_id` 只指向顶层评论；对回复再回复时仍挂同一顶层评论，另用 `reply_to_user_id` 记录"回复给谁"——**拒绝第三级及更深嵌套**，否则渲染、分页、删除连带都会失控。② **计数口径**：文章 `comment_count` = 顶层评论数 + 回复数（回复也算评论）。③ **排序**：顶层按时间倒序、同一顶层下回复按时间正序；**回复不改变顶层排序**。④ **删除连带**：删顶层 → 其下回复全部软删，计数减 `1 + 回复数`；删单条回复 → 减 1；两者都同步清理 `forum_comment_likes`。⑤ **点赞**：顶层与回复都可点赞，切换幂等，`forum_comment_likes` 与 `forum_comments.like_count` **同事务**提交（同 D6）。⑥ **回复不做分页**：单条顶层评论的回复一次全返（社区规模可接受；超 30 条折叠留第二阶段）。⑦ **回复不触发通知**——站内信在第二阶段，被回复者只能自己回来看，这是明确接受的缺口 |
| **D16** | 评论不提供作者自删 | 第一阶段**评论区不提供删除入口**，评论治理统一由管理员在后台抽屉处置（§6.1.5、§0.3-A）。理由：评论删除的权限边界（谁能删、删顶层是否误伤他人回复）在第一阶段不值得开这个口子；"作者删除自己的评论"列第二阶段（§12.1） |

## 9. 项目规约与落地约束（防踩坑）

实施时必须遵守仓库既有约定，以下为**本模块特别相关**的条目：

1. **统一 `/api` 前缀**：模块 router 只声明 `prefix="/forum"`，`/api` 由 `main.py` 全局挂载。**前端 `api.js` 里每条路径都要显式写 `/api/forum/...`**——本项目前端**没有**改 `baseURL`，是在路径里手写 `/api` 的（改 baseURL 会变成 `/api/api/...`）。
2. **响应包络**：所有接口 `{code, message, data}`，前端 axios 拦截器已统一解包，**组件里不要再判 `code`**；后台 `PureHttp` 已统一解包并把错误提到 `error.message`，页面 catch 里直接 `ElMessage.error(e.message)`。
3. **字段命名**：库内 snake_case，对外 camelCase（Pydantic `alias` + `populate_by_name=True`）。新增字段**必须同时补别名**，否则前端拿到 snake_case。
4. **时间**：`String(30)` + 北京时间 ISO 字符串（`crud._TZ`），**不用 `DateTime`**。
5. **布尔语义用 int**：`isTop` / `isFeatured` / `isHot` / `isHidden` / `isSystem` 一律 `0/1`，不改 bool。
6. **新表直接 `create_all`**：新表不需要 `migrate_*` 补列函数；**只有 `users.mute_until` 这一存量表补列**需要写幂等迁移。
7. **静态资源引用**：模板内引用的静态图片必须先 `import` 再绑定 `:src`，**禁止写 `/src/...` 绝对路径**（build 后 404，dev 看不出来）。
8. **文档同步**：改动完成需同步 `AGENTS.md`（新增「论坛模块规约」小节）、`README.md`（接口表 + 页面路由表 + 环境变量表）、`TODO.md`（第二阶段顺延项）、`admin-frontend` 菜单。
9. **组件复用（依据文档落地建议）**：帖子卡片、侧边栏用户卡、评论区抽为独立组件；`props` 驱动；后续阶段只扩 props 不改结构。
10. **扩展点预留（依据文档落地建议）**：站内信图标、打赏按钮、`+ 关注`按钮第一阶段只做 UI 占位，但**路由与状态管理位置要留好**——占位组件与被占位功能放在同一目录/同一命名空间，避免第二阶段重构搬文件。
11. **`dev.bat` / `dev.sh`**：若两个新页面需要在本地起服验证，沿用现有脚本，不新增脚本。
12. **发布与编辑共用同一套写路径**：创建（`POST`）与编辑重提（`PUT`）必须共用同一份实现——同一组字段校验、同一个摘要生成函数、同一套标签同步与 `use_count` 处理。**不要复制两份**，否则编辑路径一定会漏掉摘要重算或标签计数，产生"改了正文但摘要还是旧的"这类静默不一致。
13. **前端权限只是体验，不是防线**：`/forum/edit/:id` 的 404 处理、隐藏「编辑」按钮都只是体验层；后端必须独立校验"当前用户 == author_id"与状态准入，不接受任何前端传入的状态或作者字段。
