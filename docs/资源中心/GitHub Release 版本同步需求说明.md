# GitHub Release 版本同步需求说明（最终版）

## 一、核心目标与原则

- **唯一标识**：以资源级别的 **`GitHub Tag`** 作为匹配版本的唯一依据。同一资源下，Tag 不允许重复。
- **双轨同步机制**：
  1. **批量同步（只增不改）**：每次拉取最新的 20 条 Release，本地存在的 Tag 直接跳过，只新增没有的版本。
  2. **单版本同步（覆盖更新）**：针对已有版本，允许手动触发单条同步，用 GitHub 的最新数据**覆盖**本地对应字段（仅覆盖 GitHub 能提供的数据）。
- **触发方式**：支持后台手动触发批量、手动触发单个、以及每天凌晨的定时自动触发（仅批量）。
- **鉴权方式**：通过后端 `.env` 文件配置 GitHub PAT Token，提升 API 频率限制并确保稳定访问。

## 二、环境变量与鉴权配置

1. **环境变量**：
   - 在项目的 `.env`（及 `.env.example`）中新增配置项：`GITHUB_PAT=你的_token_字符串`。
   - 后端配置加载需支持该变量，允许为空（为空时降级为未认证请求，并记录警告日志）。
2. **请求头注入**：
   - 请求 GitHub API 时，若 `GITHUB_PAT` 存在且非空，必须注入 Header：
     `Authorization: Bearer ${GITHUB_PAT}`
   - 必须附加 Header：`Accept: application/vnd.github+json` 和 `X-GitHub-Api-Version: 2022-11-28`。
3. **安全红线**：
   - **绝对禁止**在 API 响应、前端日志或后端错误堆栈中返回或打印 Token 明文。

## 三、触发机制与 UI 交互

### 1. 批量同步
- **手动触发**：在管理后台的【资源管理 - 版本与资产列表页】右上角，增加 **[同步 GitHub Release]** 按钮。
  - 点击后触发批量同步，按钮展示 Loading。
  - 完成后提示：`同步完成：新增 X 个版本，跳过 Y 个已存在版本。`
- **定时触发**：每天凌晨（如 03:00）执行一次全局扫描。遍历所有状态为“已发布”且有合法 GitHub 仓库地址的资源执行批量同步，记录日志。

### 2. 单版本精准同步（新增需求）
- **UI 位置**：在【版本与资产列表页】中，每个版本卡片（如 1.2.0 所在区域）的右上角操作栏，在“编辑”旁边新增 **[同步 Release]** 按钮。
- **交互确认**：点击后弹出确认框：“确定要使用 GitHub 上的最新数据覆盖此版本信息吗？您手动填写的兼容游戏版本、平台等信息不会被覆盖。”
- **API 调用**：调用 `GET /repos/{owner}/{repo}/releases/tags/{tag_name}` 精准获取该 Tag 对应的 Release 详情。
- **异常处理**：如果返回 404，提示“该 Tag 在 GitHub 上不存在，可能已被删除”。

## 四、处理流程与映射规则

### 1. 批量同步流程（限制 20 条）
1. **解析仓库地址**：从资源的 `GitHub 仓库` 字段中提取 `owner` 和 `repo`。
2. **拉取数据**：调用 `GET /repos/{owner}/{repo}/releases?per_page=20`。
3. **过滤数据**：过滤掉 `draft == true` 的记录；过滤掉 `Source code (zip/tar.gz)` 资产。
4. **比对与新增**：查询本地已有的 `github_tag` 列表，跳过已存在的，对于不存在的执行新增。
   - 新增版本记录，并遍历 `assets` 创建 `version_assets` 记录（建议使用事务）。

### 2. 单版本覆盖流程
1. 根据当前版本的 `github_tag`，请求 GitHub API 获取单条 Release 详情。
2. 校验成功后，更新本地的 `resource_versions` 和 `version_assets` 记录。

### 3. 字段映射与覆盖规则（重要）

| 本地字段 | GitHub API 字段 | 批量新增规则 | 单版本覆盖规则 |
| :--- | :--- | :--- | :--- |
| **GitHub Tag** | `tag_name` | 填入并设为只读。 | 忽略（作为查询条件，不修改）。 |
| **版本号** | `tag_name` | 去除 `v` 前缀后填入。 | **覆盖**（如果 GitHub 变了，本地也跟着变）。 |
| **发布渠道** | `prerelease` | `true` 为 `Beta`，`false` 为 `Stable`。 | **覆盖**（自动更新本地渠道）。 |
| **发布日期** | `published_at` | 格式化为 `YYYY-MM-DD` 填入。 | **覆盖**。 |
| **更新日志** | `body` | 填入。 | **覆盖**（用 GitHub 最新内容替换）。 |
| **状态** | 无 | 默认 **隐藏**。 | **不覆盖**（保留本地设置）。 |
| **最新稳定版** | 无 | 默认 `false`。 | **不覆盖**（保留本地设置）。 |
| **兼容游戏版本/平台/运行环境** | 无 | 默认为空或继承资源级。 | **不覆盖**（保留管理员手工填写的核心元数据）。 |
| **版本下资产** | `assets` | 新建资产记录。 | **完全覆盖**。删除该版本下所有自动同步来的资产，重新插入最新的资产列表。 |

## 五、后台 UI 补充要求

1. **资源编辑表单**：`GitHub 仓库` 字段必须以 `https://github.com/` 开头。
2. **版本列表页**：顶部有批量同步按钮和“上次同步时间”展示；每个版本卡片上有单版本同步按钮。
3. **版本编辑弹窗**：由同步生成的版本，`GitHub Tag` 字段禁用（只读）。管理员在此处可补充兼容版本、平台等。

## 六、异常处理

- **API 限流**：捕获 `403/429`，提示“API 达到速率限制”。
- **网络超时**：请求超时（如 10 秒），最多重试 2 次。
- **访问失败**：`404` 提示“无法访问仓库或 Tag 不存在”。
