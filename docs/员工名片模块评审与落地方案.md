## 1. 需求在做什么（浓缩）

一句话：**给管理组成员发一张"只证明身份、不授予任何权限"的名片；扫码跳到官网验证页；后台能撤销、能续期，二维码长期复用。**

- 名片 = 服务器名 + 像素头像 + 游戏ID + 职务 + 职责 + 版本 + 二维码（需求 §3.1）
- 验证页 = `/staff/{身份码}`，只读、不含隐私、四种状态（有效 / 已撤销 / 已过期 / 未找到）（需求 §6、§9.1）
- 后台 = 工作人员台账 + 身份码生成 + 二维码/名片出图 + 撤销 + 续期 + 查询日志（需求 §8；**查询日志 P0 不做、顺延 P1**，§4.7）
- 硬红线 = 名片与验证页不得出现真实姓名、手机号、住址、后台/RCON/数据库地址、任何密码与令牌（需求 §3.3）
- 明确**不做**：短信/邮箱验证码、动态口令、活体检测、区块链、NFC、数字签名、自动刷新、玩家登录、独立管理员账号系统（需求 §4.2）

范围控制得很克制，这是这份需求最好的地方。

**拍板**：不引入 `expired` 状态；查询时 `now > valid_to` 即为已过期，此时把 `active` 更新为 `revoked`；需求 §8.4 的「系统定时检查并更新状态」逻辑**保留**。

即：库内 `status` 仍只有 `active` / `revoked` 两态（不新增第三态），但**过期是"会写库的"**——由统一的到期检查函数完成，触发时机有两处：

| 触发 | 时机 | 作用 |
|---|---|---|
| **查询时懒更新** | `GET /api/staff/public/{code}` 命中一条 `status='active'` 且已过期 | 立刻写 `status='revoked'`、`revoked_reason='expired'`、`revoked_at=now`，再返回 |
| **定时批量检查** | `staff_expire.py`（CLI，仿 `kb_sync.py`）+ crontab 每日一次；`main.py` 启动时也执行一次 | 兜底全表扫描，把"没人扫过"的过期名片也刷成 `revoked`（台账可视性） |

两条路径**共用同一个函数**（`expire_due(session, only_id=None)`），保证语义唯一。

关键规则（漏一条就坏）：

1. **幂等**：仅当 `status == 'active'` 且已过期时才写库；第二次读到已是 `revoked`，不再写。→ 公开接口不会因过期产生持续写放大。
2. ✅ **`valid_to` 才是权威，`status` 只是快照**。任何判定都必须以 `now > valid_to` 为准（**不是**以 `status` 为准）。这样定时任务漏跑、早跑、甚至完全不跑，都不会出现"已过期却显示有效"——查询路径必然兜住。**这一条把原设计最担心的"定时器漏跑 = 假阳性"风险直接消灭。**
3. ✅ **续期必须能救回**：需求 §5 要求"续期后不需要玩家重新扫码"，所以到期后**不能靠重生成码**。`renew` 规则：
   - `status='revoked'` 且 `revoked_reason='expired'` → **自动恢复为 `active`**、清空 `revoked_at` / `revoked_reason`，再延长 `valid_to`（+1 年）；
   - `revoked_reason` 为人工撤销（`离职/转岗/暂停/码异常`）→ **拒绝续期**（HTTP 400），必须先走 `restore`（`restore` 会换新码，符合需求 §8.1）。
   - 缺这条规则 → 续期后名片仍是"已失效"，而台账显示"已续期"，**静默不一致**（已列为 §9 风险）。
4. **原因枚举增加 `expired`**：`revoked_reason ∈ {离职, 转岗, 暂停, 码异常, expired}`。前四项由人工选择，`expired` **只由系统写入**，后台下拉框不得出现。
5. **展示态区分**（需求 §6 有"已撤销"与"已过期"两套文案，必须能区分）：后端 `derive_state()` 输出四态——
   `expired`（`revoked` 且 `reason=expired`）/ `revoked`（其余）/ `valid` / `not_found`；前端据此选文案。
6. **台账过滤双保险**：列表页按状态过滤时，条件写成 `status='revoked' OR valid_to < :now`，避免"crontab 未跑 + 无人扫码"期间漏筛。状态列展示同理，必要时在 SQL 层 `CASE WHEN valid_to < :now THEN 'expired'`。

与本文早期版本（`expired` 纯派生、完全不写库）的差异及可接受性：

- 原顾虑两条——「定时器 + 续期回写耦合」与「漏跑即假阳性」。**规则 2 消灭了后者，规则 3 消灭了前者**。
- 唯一残留代价：`status` 会随时间被系统改写（最长滞后一个 cron 周期）。这在台账里是**符合直觉**的（服主看到的就是"已过期"），且规则 6 已兜住筛选口径。
- 实际收益：后台可直接用 SQL 过滤状态，不必把"过期"写成复杂表达式；也让"过期"这件事在库里留下痕迹（谁都可以查证何时失效）。

### 4.6 ⏸ 限流：P0 不做（拍板顺延 P1，设计原样保留）

**拍板：先不做限流，登记 `TODO.md`。** 以下设计原样保留，P1 启用时直接取用。

P0 的替代防线与必须承认的后果：

- **"枚举"在算术上不可行**：身份码 12 位 × **32 字符表**（全小写，2026-09-25 拍板）→ 32¹² ≈ **1.15×10¹⁸** 种。即便以 1000 QPS 遍历也要 **3.6×10⁷ 年**量级。字符集从 57 缩到 32 把熵由 ~1.3×10²¹ 降到 1.15×10¹⁸，**不改变"枚举不可行"的结论**。所以取消应用层限流**不会导致身份被猜中**，损失的只是"防高频刷量"这一层。
- P0 的兜底可放在 **Nginx 层**（`limit_req` / 连接数限制），或先接受无应用层限流。
- 未命中路径的**统一文案与统一响应**（§6.2）不受影响，不因取消限流而放宽一致性要求。

设计（P1 启用时照此实现）：

需求 §10.1「异常高频查询自动临时限制」+ §6.4「记录异常查询，防止有人批量扫描有效身份码」。

`kb.py:91-140` 的进程内滑动窗口 + `_client_ip()`（XFF → X-Real-IP → client.host）可以整段复用。但**不能照抄阈值和粒度**：

- 客服是"每分钟 5 次全局"，名片验证页是**公开扫码入口**——群里发一张名片，几十人同时扫是常态。按客服口径限流会大面积误伤。
- **分级**：
  - **命中记录（active/revoked/expired）**：只做宽松的全局兜底（如 120 次/分钟/IP），正常核验基本不可能触发。
  - **未命中（not_found）**：按 IP 严格计数（如 20 次/分钟/IP），超限直接 429。防枚举只需卡住"错误码"这一路。
- 粒度是**进程内**，单 worker 部署下有效——多 worker 需换共享存储（与客服限流共用同一条遗留）。
- 配套配置（P1 再加）：`STAFF_NOTFOUND_RATE_PER_MIN`（默认 20）。

### 4.7 ⏸ 查询日志审计：P0 不做（拍板顺延 P1）

**拍板：不做日志审计，登记 `TODO.md`。P0 不建 `staff_verify_log` 表**（避免"建了表不写"的半成品状态）。

P0 因此**没有查询留痕**——事后无法回答"这个码被谁、在什么时候扫过"。这是明确接受的取舍，需求 §7.2 的 90 天留存随 P1 一并落地。

设计（P1 启用时照此实现）：

需求 §7.2 要求每次查询落 `staff_verify_log`。验证页是**匿名公开接口**，若被扫号器打，写日志本身会成为放大器（每次 404 都写一行）——因此 P1 落地时**必须与 §4.6 的限流同时上线**，两者是一对。

**要点**：`not_found` 全量记录（这才是审计要看的东西）+ 其余各态记录；用限流把写入速率封顶。清理用**启动时执行一次** `DELETE WHERE create_time < now - 90d`（需求 §7.2「至少保存 90 天」），可选挂 crontab——不引入新框架。

### 4.8 ⏸ 中文字体：按拍板忽略（生产非 Docker 部署）

**拍板：生产环境不是 Docker 部署，忽略该项。**

补充一句边界（不改变结论）：这项的**根因是"宿主机没有 CJK 字体"，不是"Docker"本身**。

- 生产若为 **Windows / 带桌面的 Linux**：系统中文字体已存在，Pillow 直接指向系统字体即可（如 `C:/Windows/Fonts/msyh.ttc`），问题不存在。
- 生产若为**精简 Linux**（无字体包）：P1 真要做服务端渲染时仍会遇到豆腐块，届时 `apt/yum install` 字体、或把字体文件提交进仓库（`backend/assets/fonts/`，与部署方式无关的方案）都能解决。
- **P0 完全不受影响**：P0 走前端出图（§6.5），浏览器用系统字体，后端不渲染任何文字。

→ 结论：**P0 不处理；P1 若启用服务端渲染，按上面第二条择一即可。**

### 4.9 ✅ PDF 导出：前端直接调浏览器打印 API，后端不引依赖

**拍板：PDF 由前端直接调用浏览器打印 API，后端不额外引包。**

需求 §8.3 要"导出 PNG、JPG 和 PDF"。**不引 reportlab / fpdf**：

- **浏览器打印 → PDF（P0 唯一路径）**：矢量输出，打印最清晰，模板 HTML 已实现（`window.print()` + `@media print` 分页）。

- Pillow 的 `img.save(path, "PDF", resolution=300)` 只在 P1 服务端渲染时可能用到，**P0 不涉及**。

### 6.1 数据层（`backend/app/database.py` 追加 **1 张表**，不新建包）

```python
class Staff(Base):
    """工作人员名片台账。status 仅 active / revoked 两态（无 expired）；
    过期由 now > valid_to 判定，命中时把 active 回写为 revoked（reason='expired'）——见 §4.5。"""
    __tablename__ = "staff"

    id:            int PK
    staff_code:    String(32)  unique index   # 完整身份码（唯一，对外不下发）
    display_code:  String(16)                 # 展示码（页面只回后四位）
    game_id:       String(50)
    nickname:      String(50)  nullable       # 公开昵称
    role:          String(30)                 # 服主/技术员/财务/管理员/建筑/客服
    duty:          Text                       # 职责范围
    avatar_path:   String(512) default ""     # 头像相对 URL
    public_email:  String(255) nullable       # 工作邮箱（可空）
    status:        String(16)  default "active"   # active | revoked（枚举字符串，参照 KBDocument.status）
    card_version:  String(16)  default "V1"
    valid_from:    String(30)
    valid_to:      String(30)
    remark:        String(255) default ""     # 内部备注，任何对外响应都不下发
    create_time:   String(30)
    update_time:   String(30)
    revoked_at:    String(30)  nullable
    revoked_reason: String(30) default ""     # 离职|转岗|暂停|码异常|expired（expired 仅系统写入，后台不可选）
```

⚠️ **`staff_verify_log` 表 P0 不建**（§4.7 拍板：不做日志审计）。结构设计保留如下，P1 启用时原样照建：

```python
class StaffVerifyLog(Base):        # ← P1，P0 不落地
    """查询日志（安全审计用，不关联玩家游戏ID/聊天/个人信息）。"""

要点：

- **P0 只有 1 张新表**，`Base.metadata.create_all` 自动建，不必动 `migrate_*` 系列函数。（P1 补 `StaffVerifyLog` 同理，无需迁移脚本。）

- 全表**没有任何隐私字段**（无真实姓名/手机号/住址/身份证），需求 §3.3 从数据层就天然满足。

实现要点：

| 项 | 做法 |
|---|---|
| **身份码生成** | `secrets.choice` 从 **32 字符表**（小写字母 + 数字 = 36，去掉 `0` `1` `l` `o`，即 `23456789abcdefghijkmnpqrstuvwxyz`）取 12 位；插入前查重，冲突重试。熵 = 12 × log₂32 = **60 bit**，远超需求"至少 10 位"。**全小写**（2026-09-25 拍板）→ 查询侧不做大小写归一，只 `strip()` |
| **二维码** | `qrcode` 库，`error_correction=ERROR_CORRECT_M`（= 需求 §8.2「中等」）、`border=4`（= 需求「四周保留空白」quiet zone）、`box_size=10`。**URL 由后端拼**：`f"{STAFF_PUBLIC_BASE_URL}/staff/{staff_code}"`，绝不接受前端传 URL。**版本交给库自动选——实测落到 v4，见 §6.2.1** |
| **状态判定（权威）** | 判定只看 `valid_to`：`now > valid_to` 即已过期。唯一函数 `derive_state(row)` 输出 `valid` / `revoked`（人工撤销）/ `expired`（`revoked` 且 `reason='expired'`）；`not_found` 由其上层处理（§4.5 规则 2、5） |
| **到期回写** | `expire_due(session, only_id=None)`：把 `status='active'` 且 `now > valid_to` 的行写为 `status='revoked'`、`revoked_reason='expired'`、`revoked_at=now`。**幂等**（仅 active→revoked 写一次）。两个调用点：查询命中时（传 `only_id`）+ 定时批量（§4.5） |
| **定时检查** | `backend/staff_expire.py`（CLI，仿 `kb_sync.py`）+ crontab 每日一次；`main.py` 启动时也跑一次。**crontab 不跑也不影响正确性**（查询路径兜底），只影响台账刷新时效 |
| **未找到** | 无论"格式非法"还是"确实不存在"，**统一**返回同一文案与同一 `state='not_found'`，不暴露判断逻辑（需求 §6.4、§10.1） |
| **限流 / 日志** | ⏸ **P0 均不做**（§4.6 / §4.7 拍板）：不引滑动窗口、不建 `staff_verify_log` 表、不写查询日志。P1 启用时两者**必须同时上线**（限流负责把写入速率封顶） |
| **恢复语义** | `restore` 若原状态为 revoked（含 `reason='expired'`）→ 清空 `revoked_at/reason`、**重新生成 `staff_code`**、`card_version` 自增（需求 §8.1 明文要求） |
| **续期语义** | `renew` 延长 `valid_to` +1 年；**若该行是因到期而 `revoked`（`reason='expired'`）→ 自动恢复为 `active` 并清空 `revoked_at/reason`**（否则续期后仍显示失效）；若为人工撤销 → 400，须先 `restore`（会换码）。见 §4.5 规则 3 |
| **响应模型** | 公开响应**独立 Pydantic 模型白名单**：不含 `remark`、不含 `staff_code` 完整值（只给 `displayCode` 后四位）、不含 `id` 之外的内部字段 |
| **头像上传** | **直接复用** `POST /api/announcement/upload/image`（png/jpg/gif/webp、≤5MB、随机名、按月份分目录），零新增代码 |

结构        https://  +  xqly.xt91tv.shop  +  :23333  +  /staff/  +  身份码(12)
长度        8 + 16 + 6 + 7 + 12 = 49 字节
```

| 项 | 计算 | 结论 |
|---|---|---|
| 字符模式 | 含 `:` `/` 小写字母 → 非纯大写数字集，走 **Byte 模式** | 按字节数算容量。**身份码改全小写（2026-09-25）后仍含小写字母，模式不变**，版本结论不受影响。（注：QR 的 alphanumeric 模式只收大写字母 + 数字，理论上"全大写"能压得更小，但会牺牲手抄可读性，与 §0.3 定稿相悖，不做此优化。） |
| QR 版本 | Byte 模式 + 纠错 M 的容量：v1=14 / v2=26 / **v3=42** / **v4=62** 字节；49 > 42 → 落 **版本 4** | **33×33 模块**，比需求示例（无端口）高一档 |
| 关键动作 | **禁止硬编码 `version=`** | 域名/身份码长度将来若有变动，硬编码会直接抛 `DataOverflowError`；交给 `qrcode.make()` 自动选版 |
| 身份码长度复核 | 若想压回 v3（≤42 字节），身份码须 ≤5 位——**熵不足，不可接受** | **维持 12 位 / v4**，不要再试图"为了二维码小一点"去砍身份码 |
| 生成参数 | `box_size=10` → PNG 为 (33+8)×10 = **410×410 px** | 后台下载的 PNG 足够大，印刷不糊；前端展示再 CSS 缩放 |
| 整体物理尺寸 | 33 模块 + 两侧各 4 模块留白 = **41 模块**。经验阈值：单模块 ≥0.4mm（0.33mm 为下限，油墨扩散/弱光/低端镜头下易失败） | 二维码**整体（含留白）≥ 20mm** |
| **模板须改** | 模板 `.qrcode` 是 `166px` / `.card` 是 `900px`。若按标准名片 90mm×54mm 印刷 → 0.1mm/px，166px = 16.6mm，扣掉 9px padding 后 QR 本体仅 148px ≈ 14.8mm → **约 0.36mm/模块，低于 0.4mm 阈值** | **把 `.qrcode` 从 `166px` 提到 `200px`**（横竖版同步）→ QR 本体 182px ≈ 18.2mm → **约 0.44mm/模块，过阈值**。卡面按其他尺寸印刷时，用"模块边长 ≥0.4mm"反算 |
| 纠错级别 | 需求 §8.2 定死"中等"= M | 维持 M。**若四款 App 实测发现失败率高，升到 Q（25%）只让版本 +1（v5 = 37×37），是成本最低的鲁棒性提升**——远比换域名/换端口便宜 |
| 颜色 | 深色码点 + **纯白底** | 模板 `.qrcode` 已是 `background-color:#fff` ✅。⚠️ 卡片底色是深色（`--bg-3: #0d141f`），**改造模板时绝不能为了"背景统一"把二维码底改成透明或深色**——那样扫码直接失效。需求 §8.3 的"背景统一"指卡片风格，不适用于二维码承载区 |
| 隐私 | URL 里只有 `域名 + /staff/ + 随机码` | 需求 §8.2「不允许二维码内容直接包含电话、邮箱、微信等隐私字段」由后端拼接天然满足（前端没有拼接权） |

> 顺带排除一个疑点：**`:23333` 只增加 6 字节、不改变版本结论**（去掉端口是 43 字节，仍在 v4 区间内，仅比 v3 上限多 1 字节）。所以"为了二维码更小而去掉端口"没有收益——**端口是否迁移到 443，只应由 §3.1 检查项 2 的扫码兼容性实测决定**。
