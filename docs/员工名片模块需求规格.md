## 一、项目目标

为服务器制作一套统一的"工作人员名片"。名片主要在网上发送，也可以打印后线下分发。

名片的作用只有两点：

1. 向玩家介绍服务器存在这名工作人员；
2. 说明这名工作人员负责什么事务。

名片**不代表任何权限**，不用于登录服务器、管理后台、支付授权或身份交易。玩家扫码后进入官网验证页，页面从服务器后台读取最新信息，确认名片对应的游戏ID、职务、职责和当前是否有效。

〔修订 v1.1〕验证页挂在**官网同域**下，对外地址为 `https://xqly.xt91tv.shop:23333/staff/{身份码}`；二维码链接与验证页均使用 HTTPS（§10.3）。

## 二、角色与职责

| 角色 | 权限 |
|---|---|
| 服主 | 审核名片信息、批准发布、撤销身份、设置有效期、监督安全 |
| 技术员 | 开发系统、生成身份码、配置二维码、维护系统、处理安全事件 |
| 工作人员 | 提出修改申请，不能自行发布或修改自己的名片 |
| 玩家 | 只能查看验证页，不能修改任何数据 |

任何人不得在名片上公开密码、验证码、支付密码、服务器后台地址、RCON地址、数据库连接信息、私人手机号或真实地址。

〔修订 v1.1〕"服主 / 技术员"的账号体系**直接复用现有统一后台**（JWT 登录 + 管理员角色校验），不新建账号系统；后台入口位于 `/admin/`，与官网主站同域。

## 四、二维码与身份码

### 4.1 基本规则

每名工作人员拥有一个固定身份码。

二维码内容：

```text
https://xqly.xt91tv.shop:23333/staff/{身份码}
```

例如：

```text
https://xqly.xt91tv.shop:23333/staff/a3kq7mxpl
```

〔修订 v1.1〕补充约束：

- **URL 由后端拼接**（`f"{STAFF_PUBLIC_BASE_URL}/staff/{staff_code}"`），前端不得拼接、不得传入 URL——`STAFF_PUBLIC_BASE_URL` 是二维码前缀的唯一来源，换域名只改一处配置。
- 实际 URL 长度 **49 字节**（`https://` 8 + 域名 16 + `:23333` 6 + `/staff/` 7 + 身份码 12），比 v1.0 示例长一档。纠错 M 下需 QR **版本 4（33×33 模块）**。
- **禁止硬编码 `version=`**——域名或身份码长度将来若有变动，硬编码会直接抛数据溢出错误；交由二维码库自动选版。

身份码规则：

- 长度 **12 位**（v1.0 要求"至少 10 位"，本版取 12 位；熵 = 12 × log₂32 = **60 bit**）；
- **只使用小写字母和数字——全小写，不允许大写字母**〔已定稿 2026-09-25 · §0.3〕；
- 不使用容易混淆的 `0`、`1`、`l`、`o`（实际字符集 **32** 个：`23456789abcdefghijkmnpqrstuvwxyz`）；
- 使用安全随机算法生成（`secrets`），插入前查重，冲突重试；
- 校验 / 查询时**不做大小写归一**（本来就只有小写），只做 `strip()`，避免把粘贴带来的空白误判成"码不存在"；
- 字符集改为全小写**不影响二维码版本结论**：码里含小写字母，仍走 Byte 模式，URL 仍是 49 字节 → 版本 4（§8.2）；
- 生成后默认长期绑定该工作人员；
- 不要使用身份证号、手机号、QQ号或邮箱生成；
- 不要使用玩家可以猜测的连续编号；
- 不要使用"001、002"这种简单编号。

### 4.2 不需要的功能

基础版不需要以下功能：

- 短信验证码
- 邮箱验证码
- 动态一次性密码
- 实时位置
- 活体检测
- 区块链
- NFC
- 数字签名
- 自动刷新
- 玩家上传照片
- 玩家登录验证页
- 管理员账号系统，除非服务器已有统一后台 →〔修订 v1.1〕**服务器已有统一后台，故不再新建**（见 §0.1 第 2 条）

### 4.3 重新生成二维码的条件

出现以下情况才重新生成：

1. 工作人员离职；
2. 工作人员转岗；
3. 身份码可能泄露；
4. 名片信息发生实质性变化；
5. 服主主动要求更换；
6. 发现安全漏洞。

普通更新姓名、职务或职责时，只更新后台记录，不一定要换二维码。

〔修订 v1.1〕补充两条：

- **续期不换码**：`valid_to` 延长后，二维码内容不变，旧码继续可用（§5 要求"不需要玩家重新扫描新码"）。
- **恢复必须换码**：`restore`（恢复已撤销人员）**必须重新生成身份码**，旧码立即失效（§8.1 原文要求）。

## 五、有效期限

基础版有效期为一年。

后台字段：

```text
valid_from  生效时间
valid_to    到期时间
```

生成规则：

- 首次生成时，`valid_to` 为 `valid_from` 之后一年；
- 到期前由后台管理员续期；
- 续期后二维码可以继续使用；
- 不需要玩家重新扫描新码；
- 到期后页面显示"已过期"；
- 过期不代表该人员有问题，只代表名片需要续期。

〔修订 v1.1〕补充续期的完整语义（`renew`）：

| 记录当前状态 | 续期行为 |
|---|---|
| `active` 且未过期 | 直接延长 `valid_to` + 1 年 |
| 因**到期**而失效（`status='revoked'` 且 `revoked_reason='expired'`） | **自动恢复为 `active`**、清空 `revoked_at` / `revoked_reason`，再延长 `valid_to` + 1 年；二维码不变，旧码立即可用 |
| **人工撤销**（原因 ∈ 离职 / 转岗 / 暂停 / 码异常） | **拒绝续期**（返回 400），必须先行 `restore`（restore 会换新码） |

> 这条规则不可省：缺了它会出现"续期已成功、玩家扫码却仍显示失效"的静默不一致。

提醒机制〔修订 v1.1〕：v1.0 的"提前 30 天提醒服主或技术员"降级为**后台可见性**——台账列表对"即将到期（≤ 30 天）"的记录高亮，并在页面顶部给出统计条。**不引入邮件/短信/Webhook 服务**（§4.2 本就不想引第三方）。真要做推送，列为 P2（QQ 群机器人）。

## 六、验证页状态

状态由后端统一判定后返回，**前端不自行计算过期**。对外的四态为 `valid` / `revoked` / `expired` / `not_found`。

### 6.1 有效

页面顶部显示：

```text
✅ 工作人员身份有效
```

展示游戏ID、职务、职责、名片版本、更新时间和有效期限。

### 6.2 已撤销

页面顶部显示：

```text
❌ 该工作人员身份已失效
```

显示原因分类：

- 已离职；
- 已转岗；
- 已暂停；
- 身份码异常。

不显示旧联系方式，不提供历史操作记录。

〔修订 v1.1〕四条落地约束：

- 原因分类固定为后端枚举常量（`离职` / `转岗` / `暂停` / `码异常`），**后台只能选不能填**，避免文案漂移。
- 枚举在库里另有一个**系统专用值 `expired`**（仅由到期检查写入，**不得出现在后台下拉选项里**）。
- 撤销态响应为**白名单模型**：只返回状态与原因，**其余字段（游戏ID、职责、联系方式等）全部不返回**——这是 §6.2「不显示旧联系方式」的实现方式，不是"前端不给渲染"。

### 6.3 已过期

页面顶部显示：

```text
⏰ 该名片已超过有效期限
```

提示玩家前往官网管理组页面查看最新信息。

〔修订 v1.1〕「官网管理组页面」即总览页 `/team`，验证页需给出直达链接。

### 6.4 不存在

页面显示：

```text
⚠️ 未找到该身份记录
```

不要提示"身份码错误"或暴露系统判断逻辑。同时记录异常查询，防止有人批量扫描有效身份码。

〔修订 v1.1〕两条细化：

- **统一响应**："格式非法"与"确实不存在"必须返回**逐字节一致**的响应体与文案。
- 「记录异常查询」**P0 不做**（§7.2 顺延 P1）；P0 期间无查询留痕，这是明确接受的取舍。

### 8.4 状态检查

系统应定时执行检查：

```text
当前时间超过 valid_to
→ 自动标记为 expired
```

状态优先级：

```text
revoked ＞ expired ＞ active
```

已经撤销的记录，即使没有过期，也始终显示"已撤销"。

〔修订 v1.1〕**本节实现方式调整，语义不变**——不引入 `expired` 状态，过期改为"判定 + 回写"：

| 触发路径 | 时机 | 作用 |
|---|---|---|
| **查询时懒更新** | 验证页命中一条 `status='active'` 且 `now > valid_to` 的记录 | 立刻写 `status='revoked'`、`revoked_reason='expired'`、`revoked_at=now`，再返回 |
| **定时批量检查** | 独立 CLI（仿既有知识库同步脚本）+ crontab 每日一次；服务启动时也跑一次 | 兜底全表扫描，把"没人扫过"的过期名片也刷成 `revoked`（保证台账可见） |

两条路径**共用同一个函数**，保证语义唯一。三条硬规则：

1. **幂等**：仅当 `status='active'` 且已过期时才写库；第二次读到已是 `revoked`，不再写。→ 公开接口不会因过期产生持续写放大。
2. **`valid_to` 才是权威，`status` 只是快照**：任何判定都以 `now > valid_to` 为准，**不是**以 `status` 为准。这样即便定时任务漏挂、漏跑或完全不跑，也不会出现"已过期却显示有效"——查询路径必然兜住。
3. **判定与展示**：后端输出四态 `valid` / `revoked`（人工撤销）/ `expired`（`revoked` 且 `reason='expired'`）/ `not_found`，前端据 `state` 取文案（§6）。台账列表筛选同时用 `status='revoked' OR valid_to < :now` 双保险，避免定时任务未跑 + 无人扫码期间漏筛。

## 十、安全要求

### 10.1 身份码

- 使用安全随机算法生成；
- 长度至少10位；
- 后台存储只用于查询和审计；
- 不通过接口返回完整身份码列表；
- 不允许玩家批量枚举；
- 异常高频查询自动临时限制；
- 查询失败不区分"码错误"和"码不存在"。

〔修订 v1.1〕逐条落地口径：

| 原要求 | 落地 |
|---|---|
| 安全随机算法 | `secrets.choice`，**32 字符表**（小写字母 + 数字，去掉 `0` `1` `l` `o`）取 12 位；插入查重，冲突重试 |
| 长度至少 10 位 | **12 位**，全小写（熵 = 12 × log₂32 = **60 bit**） |
| 不返回完整身份码列表 | 公开接口一律不吐完整码；**导出名单接口仅管理员可调**（§8.1），豁免关系记入 `AGENTS.md` |
| 不允许玩家批量枚举 | ⏸ **P0 不做应用层限流**（见下），P0 依靠"熵足够高、枚举不可行" |
| 异常高频查询自动临时限制 | ⏸ **P0 不做**，顺延 P1（登记 `TODO.md`）。P0 可在 Nginx 层做连接数/请求速率兜底，或明确接受无应用层限流 |
| 查询失败不区分 | 统一返回同一响应体与文案（§6.4） |

> **为什么 P0 可以不做限流**：身份码 12 位 × 32 字符表 = 32¹² ≈ **1.15×10¹⁸** 种组合，即便 1000 QPS 遍历也需 **3.6×10⁷ 年**量级。字符集改全小写把熵从 ~1.3×10²¹ 降到 1.15×10¹⁸，**不改变"枚举不可行"的结论**。取消应用层限流**不会导致身份被猜中**，损失的只是"防高频刷量"这一层。
>
> **P1 设计（启用时直接取用）**：复用现有进程内滑动窗口实现，但**必须分级**——客服口径（每分钟 5 次全局）会让"群里发一张名片、几十人同扫"大面积误伤。命中记录走宽松兜底（约 120 次/分/IP），未命中按 IP 严格计数（约 20 次/分/IP）超限返回 429。限流粒度是进程内，多 worker 部署需换共享存储。
>
> **P1 必须与 §7.2 的日志审计同批上线**：日志写入需要限流把速率封顶，否则公开接口被刷时，写日志本身会成为放大器。

### 10.2 后台访问

后台至少做到：

- 仅限服主和技术员访问；
- 不使用默认密码；
- 使用强密码；
- 不把后台地址公开到官网首页；
- 定期更新后台密码；
- 不使用共享账号长期操作；
- 记录关键操作；
- 离职人员立即删除后台权限。

〔修订 v1.1〕前 6 项与最后 1 项由现有统一后台体系承接（JWT + 管理员角色校验 + 用户管理页），**不新建账号系统**；「记录关键操作」P0 暂缺（与 §4.7 一并顺延 P1）。

### 10.3 文件安全

- 头像限制文件类型；
- 头像限制文件大小；
- 不执行上传文件；
- 不显示服务器目录；
- 不返回数据库错误详情；
- 验证页使用HTTPS；
- 二维码链接使用HTTPS。

〔修订 v1.1〕前 5 项由现有上传接口承接（类型白名单 + ≤5MB + 随机文件名）；后 2 项 **✅ 已满足**（站点已配 HTTPS）。注意：头像存放目录是公开静态托管，头像本身就要公开，可接受；但**私有文件绝不能放进该目录**。

### 10.4 第三方服务

不建议依赖以下服务长期保存核心数据：

- 个人网盘；
- 普通短链平台；
- 普通二维码生成平台；
- 临时文件分享平台；
- 会插入广告的平台；
- 无法导出数据的平台。

二维码可以使用离线生成工具，但验证页必须放在服务器自己的官网或可控域名下。

〔修订 v1.1〕本版进一步收紧：名片模板原本依赖公共 CDN 加载出图库，**改为本地依赖**，使出图链路完全离线可用（§8.3）。

### 10.5 域名与端口的长期性约束〔新增 v1.1〕

二维码里固化了四段不可变信息：`https` + 域名 + `:23333` + `/staff/`。**任意一段变更 = 已发出的全部名片作废重印**，等同于让全体持卡人走一遍 §12.4 的泄露应急流程。因此：

| # | 约束 | 说明 |
|---|---|---|
| 1 | 证书必须是**受信任 CA 签发**且 SAN 覆盖 `xqly.xt91tv.shop` | 自签或域名不匹配会让微信/QQ 内置浏览器弹安全警告甚至阻断，玩家看到的是"证书错误"而非验证页 |
| 2 | **非标准端口 23333 必须四款 App 实测通过** | 部分企业网/校园网封非标端口。若任一款失败，唯一解是迁 443——**必须在批量印名片之前决定** |
| 3 | 域名续费与备案有效期必须**晚于所有名片的有效期** | 建议续 ≥ 3 年；到期日并入"提前 30 天"提醒入口。域名过期 = 全部名片**同时**失效且无任何提示 |
| 4 | 协议不得降级为 `http` | 会导致二维码 URI 语义变化 |
| 5 | **HTTPS 证书本身要按期续签** | 现用 Let's Encrypt 通配符证书，**2026-12-24 到期**（90 天一签）。到期当天全站不可访问，所有持卡人都会扫出安全警告。注意：**换证书不影响已印名片**（域名未变），这是"停机"风险而非"重印"风险；续期后替换 `/etc/nginx/ssl/` 两文件并 `nginx -s reload` |

〔修订 v1.1〕生产 nginx 站点配置**已随仓库留档**在 `for-deploy/chaos-web.conf`（改 conf 前先读该目录 `README.md`）。名片模块**不需要改动它**：`location ^~ /api/` 已覆盖 `/api/staff/*`，兜底 `location /` 的 `try_files` 已覆盖 `/staff/:code` 与 `/team`（§4.1 的扫码直达即依赖它）。

## 十二、运行流程

### 12.1 新增工作人员

1. 工作人员提交公开信息；
2. 服主审核；
3. 技术员录入后台；
4. 系统生成固定身份码；
5. 生成二维码；
6. 生成名片图片；
7. 服主审核名片；
8. 在官网和群公告发布；
9. 开始计算一年有效期。

### 12.2 更新信息

1. 工作人员提交修改申请；
2. 服主审核；
3. 技术员更新后台；
4. 名片版本增加；
5. 生成新名片；
6. 发布新名片；
7. 说明旧名片何时失效。

若二维码没有重新生成，旧二维码仍可使用，但扫码结果会显示更新后的信息。

### 12.3 工作人员离职

1. 服主在后台撤销身份；
2. 旧身份码立即失效；
3. 官网管理组页删除该人员；
4. 旧名片停止发放；
5. 群公告更新；
6. 服内公告更新；
7. 删除该人员所有后台权限。

### 12.4 二维码泄露

1. 服主确认泄露范围；
2. 技术员重新生成身份码；
3. 生成新二维码；
4. 制作新名片；
5. 旧码立即失效；
6. 通知工作人员停止发送旧名片。

〔修订 v1.1〕12.3 与 12.4 的区别仅在于：**离职 = 撤销（`revoked`，长期失效）；泄露 = 重生成身份码（旧码立即无效，本人在册状态不变）**。二者的码都不再可查。

## 附录 A：接口清单（实施约定，非需求条款）

> 统一 `/api` 前缀由全局挂载，本模块只声明 `prefix="/staff"`。所有响应走 `{code, message, data}` 包络（`code=0` 成功），错误抛标准 `detail`。

```
GET    /api/staff/public/{code}              验证页数据（匿名，白名单模型）
GET    /api/staff/public/team                管理组总览（匿名，仅有效期内公开字段）

GET    /api/staff/admin/page                 台账分页（状态过滤 + keyword）
POST   /api/staff/admin                      新增工作人员（自动生成身份码 + valid_from/to）
PUT    /api/staff/admin/{id}                 编辑公开信息（card_version 自增）
POST   /api/staff/admin/{id}/regenerate-code 重生成身份码（旧码立即失效）
POST   /api/staff/admin/{id}/revoke          撤销（body: {reason}，仅接受 离职/转岗/暂停/码异常）
POST   /api/staff/admin/{id}/restore         恢复（必须生成新身份码）
POST   /api/staff/admin/{id}/renew           续期一年（因到期失效则自动恢复 active）
GET    /api/staff/admin/{id}/qrcode          二维码 PNG
GET    /api/staff/admin/export               导出名单 CSV（仅管理员，§10.1 豁免点）
GET    /api/staff/admin/logs                 ⏸ P1
```

新增接口必须**同步更新契约参照文件**（主站 `frontend/src/api/api.js`、后台 `admin-frontend/src/api/`），并在后台路由表登记菜单——这是项目既定规约，不是可选项。
